## 一、装配顺序:`main.ts` 是一张顺序表

`src/main.ts` 有 1152 行,其中相当大一部分是注释,注释里几乎每一段都在解释**为什么这一句必须排在那一句前面**。把这些解释抽出来,就是这个文件真正的结构。

### 1.1 构造链

```
createRenderer(canvas)                              main.ts:52
installPassStats(renderer)                          main.ts:55
new SkyTime(renderer, scene)                        main.ts:65
new CameraDirector(camera, canvas)                  main.ts:66
new LoadingVeil(uiRoot)                             main.ts:67
createQuality({ renderer, scene, sun, camera })     main.ts:70
quality.apply(store.read().quality)                 main.ts:71
director.place((26,14,30) → (0,4,0))                main.ts:74
```

两条硬顺序:

- **`installPassStats()` 必须在任何一次 render 之前**(`src/main.ts:55`)。它靠替换 `renderer.shadowMap.render` 来数阴影 pass(`src/core/passStats.ts:96-107`),装晚了就会漏掉此前发生过的所有阴影渲染。
- **`createQuality()` 传的是 `skyTime.sun`**,不是场景里随便一个平行光。阴影贴图边长这一项由 `quality.ts` 拥有,而阴影相机的其余参数由 `skyTime.ts` 拥有,两者的唯一衔接点就是这盏灯。

### 1.2 三支时钟

| 时钟 | 变量 | 停不停 | 出处 |
| --- | --- | --- | --- |
| 世界钟 | `Loop.worldTime` | 永不暂停 | `src/core/loop.ts:132` |
| 动画钟 | `animTime` | 被「动画」开关冻结 | `src/main.ts:308`、`src/main.ts:424` |
| 音频钟 | 由 `AudioEngine` 内部维护 | 不随页面停(rAF 停了音频线程照走),靠喂同一个 `worldTime` 对齐 | `src/main.ts:390` |

**为什么要给动画单独开一支钟,而不是「关掉就不调 `update()`」或「把 `worldTime` 传 0」**(`src/main.ts:291-303`):

- 前者的话,相位在关着的时候仍在偷偷走远(`worldTime` 不停),再打开的瞬间幌子 / 柳枝 / 炊烟会**跳到**新相位上。
- 后者会让水面、配乐、相机一起停摆 —— 它们不归这个开关管。
- 所以只给被开关管辖的那三层另开一支,由**同一个 dt** 累加:**全作品仍然只有一个时间源,这里只是多了一道闸门**。喂进去的是**绝对相位**而不是 `dt`,风动是周期函数,累积 `dt` 会在切标签页回来时把幌子甩到别的相位上,而且再也回不去(`src/main.ts:401-406`)。

`animTime` 与 `animDt` 必须在 `store.subscribe()` **之前**声明(`src/main.ts:305-306`),理由和下面第 13.4 节的哨兵值是同一类:订阅会立即同步推一次当前值,回调里会读这两个变量,而放到订阅下面就是 **TDZ 报错**。

**为什么音频不读 `Date.now()`**:切标签页回来时浏览器会把 `rAF` 停掉,但音频线程还在走。两边一旦各读各的时钟就会整体错位。所以音频调度喂的是循环里那个唯一的 `worldTime`,引擎内部再用漂移量做自愈(`src/main.ts:387-390` 的注释)。

### 1.3 逐环计时表

`src/main.ts:384` 起的 `stages: Stage[]` 是一张"每一环单独跑一遍要多久"的表:

| 顺序 | 名称 | 时钟 | 为什么排在这里 |
| --- | --- | --- | --- |
| 1 | 天空/时辰 | world | 太阳位置、颜色、场景雾都归它改 |
| 2 | 相机 | world | 阻尼推进,只改相机 |
| 3 | 配乐 | world | 喂 `worldTime`,见 1.2 |
| 4 | 水面 | world | **必须在天空之后**:水面渲染要用本帧的太阳与雾,顺序反了会出现"岸上已是黄昏、河面还亮着"的一帧(`src/main.ts:391-395`) |
| 5 | 人物 | **anim** | 必须在 `river.update` 之后:水面反射这一帧要渲染本帧最终的人影(`src/main.ts:397-399`) |
| 6 | 道具风动 | anim | `props?.update(wt)`。**必须在 render 之前**,否则这一帧渲染的是上一帧的幌子姿态 —— 静帧里看不出来,动起来才露馅(`src/main.ts:407-409`) |
| 7 | 氛围粒子 | anim | `fx?.update(wt)`。放在最后是因为它不产出任何别的东西要读,顺序错了也不会有观感差异(`src/main.ts:410-414`) |

`frameStep(dt, worldTime, doRender)`(`src/main.ts:420`)按这张表逐条分发,并按 `st.clock` 择一喂时间(`src/main.ts:433`)。

**`clock` 为什么挂在 `Stage` 上、而不是让 `fn` 自己去读闭包里的时钟** —— 这是 `src/core/frameCost.ts:77-86` 那段注释在讲的坑:`measureStages()` 会**绕过主循环**直接调 `fn(1/60, t)` 来给各环单独计时。如果 `fn` 读的是闭包里的动画钟,那么「动画」开关一关,这里量到的就是一次空转,「人物」那一行会打印出一个漂亮的小数字,而它量的是"没干活有多快"。挂在 `Stage` 上由调用处传入,测量路径就天然看不见闸门。

### 1.4 装配与画质重跑

`assemble()`(`src/main.ts:599`)的顺序是:`scene.add` 各 chunk → `setupRiver()` → `setupActors()` → `setupEffects()` → **`quality.apply(store.read().quality)` 再来一次**(`src/main.ts:616`)。

最后这一句是必须的(`src/main.ts:609-616`):启动时那次 `apply()` 发生在 GLB 落地之前,当时场景里一个人物都没有,"最近 N 个人物投影"的名额分配是空转的。不重跑的话**人物阴影会永远不生效,而且不报任何错** —— 画面看着只是"阴影有点少",不会有人去查。重跑是幂等的(`quality.ts` 文件头声明了这一点)。

`setupActors()` 必须在 `setupRiver()` 之后:反射层的对象名单是建水面时扫场景打上的,`setupActors()` 末尾那次 `refreshReflectLayer()`(`src/main.ts:578`)会把新加的对象一并纳入。`setupEffects()` 又必须在 `setupActors()` 之后(`src/main.ts:584-589`),这样粒子永远不会被卷进反射层 —— 它们是在层扫描**之后**才进场的;反过来写不会报错,只会让反射图里多出几十片烟和鸟,而且**看不出来是哪里来的**。粒子内部另有 `qm_reflect=0` 与 `layers.set(0)` 两道兜底。

另一处同类的顺序:`scene.add()` 必须在 `quality.register()` **之前**(`src/main.ts:594-595`),因为 `register()` 会立刻按当前档位调一次 `applyQuality`。

## 二、渲染器与画面口径

`src/core/renderer.ts` 只有 77 行,句句都是 r18x 上的坑。

- **色调映射 `AgXToneMapping`,曝光 1.0**(`src/core/renderer.ts:28-29`)。注释写明:r186 起 `toneMapping` 默认是 `NoToneMapping`,不显式设置的话太阳直射与水面高光会直接削平到纯白,整体发白发灰。
- **输出 `SRGBColorSpace`**(`:33`)。注释提醒:这只管最终输出,贴图各自的 `colorSpace` 要单独设,否则法线/粗糙度会被错误地做伽马变换。
- **`PCFShadowMap`**(`:39`)。r182 起 `PCFSoftShadowMap` 已废弃并回退到 PCF,想要更软的边缘应该改用 VSM 或增大 shadow radius,而不是继续用那个枚举。
- **`stencil: false`**(`:22`)—— 不用模板缓冲,关掉省显存与带宽。
- **`setPixelRatio(min(dpr, pixelRatioCap))`,默认 cap = 2**(`:15`、`:41`)。
- **`renderer.info.autoReset = false`**(`:46`)。注释:反射、阴影、深度等额外 pass 会持续累加到 `renderer.info.render`,不关自动重置、也不每帧手动 reset 的话,drawcall / 三角面读数会**虚高十倍**。每帧的 `renderer.info.reset()` 在 `src/core/loop.ts:136`(注释里写着"不重置会严重虚报")。

**软件渲染必须显眼地标出来。** `readGpuInfo()`(`src/core/renderer.ts:57`)用 `/swiftshader|software|llvmpipe|basic render/i` 匹配 `WEBGL_debug_renderer_info` 的 `UNMASKED_RENDERER_WEBGL` 串(`:75`)。HUD 里这一项命中时会弹出一条红色警告(`src/ui/hud/PerfHud.ts:59-65`),理由写在 `:60-61`:无头 Chrome 掉到 SwiftShader 时**画面看起来是正常的,只有读数在骗人**。

## 三、主循环与帧统计

### 3.1 钳制

```
raw = timer.getDelta()                 loop.ts:130
dt  = min(raw, MAX_DT)                 loop.ts:131      MAX_DT = 1/20 (loop.ts:17)
worldTime += dt                        loop.ts:132
ring[ringIdx] = raw * 1000             loop.ts:144
```

`Loop` 的定位写在类注释里(`loop.ts:31-37`):**主循环是全作品唯一的时间源**,硬性约定是"除本文件外,任何模块都不得读 `Date.now()` / `performance.now()` / `timer.getElapsed()`"。水面、风、粒子、刚体动画一律使用本循环喂进来的 `dt` 与 `worldTime`;违反这条,切画质或切标签时就会出现跳变。(`frameCost.ts` 读时钟,是这条规定唯一的例外,理由见第 6 节。)

三件事值得单独说:

- **`MAX_DT` 的理由是"不钳制就会跳变"**(`loop.ts:11-17`):掉帧时若不钳制,水面相位、风场、人物步态都会一次性推进一大步,表现为"瞬移"或"抽搐"。钳到 50ms 后,**卡顿只让动画变慢,不会跳变**。
- **钳制只钳 `dt`,不钳进环形缓冲的那一个**。写进环形缓冲的是 `raw * 1000`(`loop.ts:144`),也就是**未钳制的原始帧时**。所以 p95/max 反映的是真实体感,而不是被钳到 50ms 的天花板。
- **`timer.connect(document)` 必须手动调**(`loop.ts:50-54`):不连接 Page Visibility 的话,从后台标签页切回来的第一帧 `getDelta()` 会是离开的总秒数,相机与所有动画会瞬间跳过去。这与 `MAX_DT`、与 `animTime` 讲的是同一件事 —— **让时间本身停住,而不是让消费者各自去猜该不该动**(`main.ts:296-298` 把这层关系点了出来)。

**环形缓冲容量 600 帧**(`RING_CAPACITY`,`loop.ts:20`),注释:60fps 下约 10 秒,足够算稳定的 p95。写满后覆盖最老的。

### 3.2 p50 / p95 / max 是怎么算出来的

`stats()`(`src/core/loop.ts:107`)的逻辑是:把环形缓冲里已有的 `n` 个样本**复制出来排序**,再按下标取:

```
sorted = Array.from(ring.subarray(0, n)).sort(升序)     loop.ts:111
pick(q) = sorted[ min(n-1, max(0, floor(q*n))) ]        loop.ts:112-113
p50 = pick(0.5)      p95 = pick(0.95)      max = sorted[n-1]
avgFps = 1000 / (sum/n)
```

三处细节:

1. `Array.from(...subarray(0, n))` 是**拷贝**,不是原地排序视图 —— 排序不会破坏环形缓冲里样本的时间顺序。
2. `pick()` 用 `floor` 取下标而不是插值,所以它是"第 k 个顺序统计量",不是严格意义上的分位数。`Math.min(n-1, ...)` 保证 `q=1` 时不会越界。
3. `avgFps` 的分子是 1000,分母是**平均帧时**,单位是毫秒。
4. 返回里的 `frames: this.frames`(`:119`)是**自启动以来的累计帧数**,不是参与本次统计的样本数 `n`。`n` 来自 `this.ringLen`(`:108`),上限是 `RING_CAPACITY = 600`(`:146`)。混淆这两个数会让"p95 是在多少个样本上算的"这一问得不到答案 —— 累计值一直在长,样本数在 600 处就封顶了。

### 3.3 为什么并列显示 avg / p95 / max

`src/ui/hud/PerfHud.ts:8-12` 写得直白:**平均值会把周期性卡顿抹平**。60fps 的平均可以是"稳定 60",也可以是"一半 120 一半 30" —— 后者体感明显更差,但平均值一样。所以 HUD 三者并列,让卡顿无处可藏。

HUD 每 12 帧才刷一次 DOM(`PerfHud.ts:70-72`),注释理由是"量具影响被测对象,这是最典型的观测者效应"。

同处还有一个范围声明(`PerfHud.ts:14-16`):**本 HUD 显示的是当前这台机器、当前这个浏览器的实测值,不是"这个作品能跑多快"的结论,更不能被当成"稳定 60fps"之类的宣传语引用。**

### 3.4 rAF 间隔不能当帧时:一个已经踩过的坑

`src/core/frameCost.ts:4-31` 记录了完整过程:无头 Chrome 空页面(不含本作品任何代码)的 rAF 回调间隔 p50 = **30.26ms**,max = 36.44ms;而作品在各画质档下的帧时 p50 分别是 low 24.26 / mid 26.33 / high 30.30 —— **high 档的"帧时"正好等于 rAF 自己的节拍**,而且那是 33Hz 的节拍。关掉 vsync(`--disable-gpu-vsync`)也只能把地板降到 17.5ms,依然是地板。

把 30.4ms 当成"作品每帧花 30 毫秒"写进报告,**是把量具的刻度上限当成了被测物的长度**。

更狠的一层在 `tools/perf/raf_floor.mjs:1-25`:这个地板本身**不稳定**(随合成器状态与机器负载变),第一版只测了一次读到 30.26ms 就写进报告说"无头 Chrome 的 rAF 节拍约 33Hz",后来重跑却读到 6.1ms。所以脚本里那句话是:**"只测一次就把它当成常数,等于用一把刻度会变的尺子去校准另一把尺子。"**

## 四、画质三档

`src/core/quality.ts` 的三档是**一张表**,`apply()` 只是把表里的值搬到对应的对象上。

### 4.1 表

| | low | mid | high |
| --- | --- | --- | --- |
| `shadowMapSize` | 0 | 2048 | 4096 |
| `characterShadows`(阴影配额) | 0 | 8 | 16 |
| `reflector.enabled` | false | true | true |
| `reflector.width × height` | 512 × 256 | 512 × 256 | 1024 × 512 |
| `reflector.everyNFrames` | 3 | 3 | 1 |
| `effectsRatio`(粒子密度) | 0 | 0.5 | 1 |
| 像素比 | 1 | `min(dpr,1.5)` | `min(dpr,2)` |

出处:`src/core/quality.ts:92-121` 与 `:123-127`。

### 4.2 low 档的反射尺寸为什么填的是真实值

`src/core/quality.ts:96-105` 是一段值得原样读的注释。low 档 `enabled: false`,但尺寸与帧距**也必须填真实值,不能填 0**。填 0 的写法把"这一档用不上"编码成了"尺寸是 0",而下游会照它做算术:`?q=low&reflect=1`(强制打开反射)于是得到 `max(2, 0) = 2`,也就是一张 **2×2** 的反射贴图 —— 水面上是一块 4 像素的糊斑,还每帧都在画,不报任何错。注释明确标注这是**实测到的(693 次 pass、RT 2×2),不是推演**。

填的是 mid 档的值,理由也写在注释里:"低档若非要开反射,该花多少"的答案应该是**已经量过、确认能看的那一档**,而不是第三个没测过的配置。

### 4.3 像素比:一处与计划书的刻意偏离

`src/core/quality.ts:84-90` 记录了偏离。计划书写的是 high 档 `min(dpr,2)`,dpr > 2.5 取 1.5。那条规则在 dpr=3 的屏幕上会让 high 得到 1.5,而 mid 本来就是 `min(dpr,1.5)=1.5` —— **两档完全一样**,用户点「精细」发现画面毫无变化,只会认为这个按钮是坏的;而且 dpr 从 2.5 到 2.6 时倍率会从 2.0 掉到 1.5,不单调。所以改成单调的 `min(dpr, 2)`。注释末尾说"这一偏离记在 docs/05"。

### 4.4 `collectSkinned()` 不缓存

`src/core/quality.ts:165`。注释里记着一次事故:曾经缓存过一次,结果缓存到的是**空数组** —— 因为 `apply()` 在 GLB 加载之前就运行了。于是人物阴影从未生效,而**没有任何报错**。这与 `src/main.ts:613-615` 的"装配后重跑一次画质"是同一个问题的两端。

### 4.5 `applyShadowSize()` 的 dispose 技巧

`src/core/quality.ts:174-195`。`size === 0` 走的是另一条路:关掉 `renderer.shadowMap.enabled` 与 `sun.castShadow`(`:175-179`)。

非 0 时有**两道必须的补丁**:

```ts
if (sun.shadow.mapSize.width !== size) {
  // ⚠️ 必须先丢掉旧的贴图,否则改 mapSize 完全无效(见文件头)
  if (sun.shadow.map) { sun.shadow.map.dispose(); sun.shadow.map = null; }
  sun.shadow.mapSize.set(size, size);
}
if (wasOff) renderer.shadowMap.needsUpdate = true;
```

第二道(`:180-182`、`:194`):从"关"切回"开"时阴影贴图是旧的甚至没被画过,必须让它重画一帧,否则会有一帧没有任何影子 —— 而且这个 bug **只在 low→mid 这条路径上出现**,不是每次都看得到。

### 4.6 `applyCharacterShadows()` 只在切换时排序

`src/core/quality.ts:204-223`。只挑"最近的 N 个蒙皮网格"投影,而这批网格**只在画质切换时排序一次**,不是每帧排。每帧排的话,人物跨过第 N 名时会出现阴影闪烁。

### 4.7 `report()` 里的结构性盲区

`src/core/quality.ts:311`:

```ts
wireframeMaterials: wireframe ? eachMaterial(() => {}) : 0,
```

这是一个**如实标注的读数盲区**:"当前有几份材质是线框态"这个问题,在 `wireframe === false` 时恒返回 0,分不清"确实是 0"和"没在数"。

同处的注释(`:308-310`)解释了为什么不改成"顺手数一遍":

> ⚠️ 这里**只数不改**。早先的写法是调一次 `applyWireframeToMaterials(true)`,那让 `report()` 变成了一个会改世界的"读"操作 —— 一个本该纯读取的诊断接口把场景改回线框,而调用它的人完全看不出来。

`applyWireframeToMaterials()`(`:247`)本身只改属性,绝不创建或替换材质。

## 五、why 三个 pass 必须分开计数

### 5.1 `renderer.info` 是累积的

`src/core/passStats.ts:6-13` 是这个小文件的全部理由。`renderer.info` 的计数是**累加**的:帧首 `reset()` 之后,阴影 pass、反射 pass、主 pass 全往上加。于是"这一帧 290 个 drawcall"到底是谁花的,从这一个数里看不出来。

阶段 4 的性能门限写着"**主 pass drawcall ≤ 220**",而注释明说:**"主 pass"这个数当时根本不存在**。拿累计值当主 pass 去比 220,**要么虚报超标,要么为了压这个虚高的数去砍本来就正常的几何,两条路都是被量具带着走**。详见 `docs/05-性能测量报告.md` 第 6 节。

### 5.2 三路计数怎么来的

| 计数 | 手段 | 出处 |
| --- | --- | --- |
| 阴影 | 包住 `renderer.shadowMap.render` | `passStats.ts:96-107` |
| 反射 | `beginReflection` / `endReflection` 显式括起来 | `passStats.ts:118`、`:126` |
| 主 pass | 总数减去上面两个 | `passStats.ts:142` |

反射那两个函数带**可重入的深度计数**(`reflDepth`,`:118-134`):只在深度 0→1 时快照并计数,1→0 时才结算差额,这样嵌套调用不会把同一段重复扣掉。

「夹住」用的是**实例上的方法替换**而不是继承 renderer(`:96-98`):"比继承 renderer 轻,也不会碰到 three 内部"。

`read()` 里的主 pass 是**减出来的**(`:142-145`):

```
main.calls      = total.calls      − shadow.calls      − reflection.calls
main.triangles  = total.triangles  − shadow.triangles  − reflection.triangles
```

注释(`:22`)说明这个减法是可靠的:**三个数相加必然等于总量,不会漏**。

### 5.3 `shadowRenders` 为什么要单独记

`src/core/passStats.ts:24-30` 记了一件"容易漏掉的实情":**反射 pass 内部那次 `renderer.render()` 自己也会再跑一遍阴影**。也就是说水面开着反射时,阴影的活儿是**干两遍**的。这不是笔误,是 three 的默认行为(`shadow.autoUpdate` 默认 true)。

所以额外记一个 `shadowRenders`:**它若等于 2,报告里就该写"阴影 pass 每帧执行两次",而不是把两次的量悄悄算进一个数里**。

`read()` 返回的字段:`total` / `shadow` / `reflection` / `main` / `shadowRenders` / `reflectionRenders` / `memory` / `programs`(`passStats.ts:136-154`)。

## 六、帧开销测量

`src/core/frameCost.ts` 是"画一帧要多少毫秒"的直接量法,也是"只有 `loop.ts` 可以读时钟"这条规定的**唯一例外** —— 理由是它量的就是时钟本身,不参与任何动画推进(`frameCost.ts:29-30`)。

### 6.1 量法

停掉 rAF → 连渲 N 帧 → `gl.finish()` 等 GPU 干完 → 总时间除以 N。这样拿到的是**这台机器画一帧的真实吞吐**,与合成器节拍、与显示器刷新率都无关。

注意注释里的边界声明(`frameCost.ts:25-27`):它与"用户看到的帧时"**不是一回事**,真机上帧时会被 vsync 钳到 16.7ms 的整数倍。这个数回答的是"离 60fps 的预算还差多少"。

### 6.2 `timedRun` 骨架

`frameCost.ts:107`:

1. 记下 `wasRunning`,然后**必须先 `loop.stop()`** —— rAF 还在跑的话它的渲染会插进来,测到的是两件事的混合。
2. **4 次预热迭代**,把驱动侧的懒分配(缓冲、状态对象)摊掉,不混进均值。
3. `gl.finish()`。
4. n 次计时迭代。
5. 原本在跑的话 `loop.start()` 恢复。

### 6.3 三条测量路径

- `measureBurst(n)`(`:139`)—— 纯绘制,**每帧都 `finish()`**。注释:否则命令只是排进队列,量到的是"提交"不是"画完"。
- `measureStep(n, step, doRender)`(`:154`)—— 跑完整的一步(逻辑 + 可选绘制)。`doRender=false` 时量到的是**纯 CPU 逻辑**。这一路存在的理由写在接口注释里(`:50-56`):连渲口径量到渲染只要 4ms,而 rAF 的间隔是 24~30ms,差的 20ms 只有两种去处 —— 逻辑,或者浏览器的合成/呈现。不把逻辑单独量一次就没法分辨,只能猜,**而猜出来的那个答案会被写进报告,而且看起来完全合理**。
  - `worldTime` 是**累加**的(`t += 1/60`)而不是固定值:若每次都喂同一个 t,风动/水面的相位就钉在一点上,量到的是"某个瞬间的逻辑"而不是"一帧的逻辑"(`:147-149`)。
  - `doRender=false` 时**不 finish**:队列里没有本步提交的活儿,此时 finish 等的是上一帧残留的 GPU 工作,那是别人的时间(`:159-160`)。
- `measureStages(n, stages)`(`:166`)—— 每环 8 次预热、n 次计时,返回 `ms` / `p95` / `share`,按耗时降序(`:189`)。接口注释(`:62-64`)明确警告:**各环是分开测的,不是在同一帧里串起来测的**,所以它回答的是"这一环自己做一遍要多久",用来定位大头足够,**拿来当"各部分之和 = 总帧时"则会有偏差**。`share` 的分母是各环中位数之和,不是总帧时(`:94`)。

## 七、WebGL 上下文丢失

`src/core/contextGuard.ts` 文件头列了三条 r186 上的事实(`:14-51`),每条都配了验证方式。

### 7.1 三条事实

文件头把这三条称为"三条 r186 的事实,都是读源码核过的,不是推测"(`contextGuard.ts:14`):

1. **`preventDefault()` 是恢复事件的前提**(①,`:16-21`)。丢失事件的默认行为是"不再尝试恢复",不阻止它 `webglcontextrestored` 永远不会来。注释还记了一个更细的事实:**three 自己已经调了**(`WebGLRenderer.js` 的 `onContextLost`),而且它的监听器在渲染器构造时就注册了 —— **永远先于**本模块执行。这里仍然自己调一次,理由是它幂等,而"恢复能工作"这件事不该依赖 three 的内部实现不被改动。
2. **three 会自己重建大部分 GPU 侧资源**(②,`:23-28`)。恢复时它的 `onContextRestore` 会调 `initGLContext()`,把 `properties` / `textures` / `geometries` / `state` 全部换成新的,于是几何、贴图、材质在下一帧按 CPU 侧那份数据重新上传。它还很仔细地保住了 `info.autoReset` 与 `shadowMap.enabled/autoUpdate/needsUpdate/type`,因为这几项会被 `initGLContext()` 重置。
3. **three 不重建渲染目标的"内容"**(③,`:30-40`)。RT 的 GPU 帧缓冲会随 `properties` 一起丢掉,而它不会自己再画一遍。更要命的是 `WebGLTextures.setTexture2D` 里那一条:

```
if ( texture.isRenderTargetTexture === false && ... ) { 上传 }
state.bindTexture( ..., textureProperties.__webglTexture, ... );
```

渲染目标贴图**走不进上传分支**,直接 bind 那个(已经是 `undefined` 的)句柄,而 `WebGLState.bindTexture` 会回退到一张空贴图。结果就是:**环境贴图变成全黑,不报错、不警告**。这正是 `RebuildHook` 存在的理由。

第 3 条带 A/B 证据(`contextGuard.ts:42-51`,脚本 `tools/perf/once/env_stale_ab.mjs`:从页面里把环境钩子换成空函数,再走一遍丢失 → 恢复):

```
环境钩子正常  → 恢复后 / 丢失前 亮度比 = 1.0000,stdDev 64.73
环境钩子被摘  → 恢复后 / 丢失前 亮度比 = 0.8107,stdDev 81.62
```

也就是说不重建环境贴图的话,恢复后画面会**暗 19%**,而且只是"变暗了、对比变强了",**控制台一个字都没有**。

注释里那段结语值得抄在这里(`contextGuard.ts:50-51`):**读源码得出的结论必须自己验一遍 —— 这是本项目反复栽跟头的地方,这次验完是对的,数据也就留在这里而不是"读代码推测的"。**

### 7.2 为什么绝不 dispose 任何东西

`contextGuard.ts:53-69`。注释先把"不是那个理由"排掉:计划书风险表 #12 写的是"r186 的 `dispose()` 会释放 CPU 端数据" —— **这句是错的**,读源码核过:`BufferGeometry.dispose()`、`Material.dispose()`、`Texture.dispose()`、甚至 `Object3D.dispose()` 都只做一件事(`dispatchEvent({type:'dispose'})`),真正的删除发生在 WebGL 侧的监听器里,删的是 GL 对象,**不碰 CPU 侧那份数组 / 图像**。

真正的理由更硬(`:63-68`):本作品**没有任何重新创建场景内容的路径**(几何与贴图全部来自 GLB,构建期就定死了)。恢复之所以能工作,靠的恰恰是"CPU 侧那份数据还在,three 重新上传一遍"。一旦在丢失时把它们 dispose 掉,恢复之后就没有任何东西可以重传 —— 场景会空掉,而且**当场看不出因果**:画面是在"恢复"之后才黑掉的。

所以那条断言(**丢失路径上 dispose 调用数为 0**)守的就是这条不许越过的线。

### 7.3 流程

- 丢失(`:135-157`):`event.preventDefault()` → `loop.stop(renderer)` → 标 `isLost` → 起一个 8 秒的定时器(`timeoutMs` 默认 8000,`:118`),超时就转到"恢复超时"状态,遮罩提供「刷新页面」按钮(`:155`)。
- 恢复(`:159-200`):逐项执行 hook,**每一项单独 try/catch**,结果记进 `lastRebuild`(`:179`)。顺序上 **先 `loop.resetTimer()` 再 `loop.start(renderer)`**(`:184`、`:192-193`)—— 否则恢复后第一帧会带着丢失期间累积的 delta,人会被瞬移出去。

两个 hook 在 `src/main.ts:492-515` 注册:环境贴图 → `skyTime.invalidateEnvironment()`,水面反射 → `river.invalidateReflection()`。

⚠️ **关于反射那一个 hook,`main.ts` 的注释明确说了它"从未单独测量过"** —— 禁用反射后那一下的代价为零,所以本文不得把它写成"实测改善"。这是有意留白,不是遗漏。

### 7.4 `diagnostics` 为什么用本地 `isLost`

`contextGuard.ts:206-221`。早期写法是 `!loop.isRunning`,那是错的:**`measureStages()` 和 `measureBurst()` 都会临时停掉循环**(见第 6.2 节),于是"正在跑性能测试"会被诊断读成"上下文丢了"。

| `azimuth`(方位角°) | 100 | 140 | 250 |

| `rayleigh` | 2.4 | 2.2 | 3.2 |

### 8.2 预设是锚点,连续量靠插值

`lerpPreset(u)`(`skyTime.ts:144`)做的是**分段**线性插值,不是三点同时加权:

```
u <= 0.5 : dawn → day,  k = u / 0.5              skyTime.ts:145-147
u >  0.5 : day  → dusk, k = (u − 0.5) / 0.5      skyTime.ts:145-147
```

理由写在 `setTimeOfDay` 的注释里(`skyTime.ts:331-333`):三点同时加权的话,`t = 0.5` 处三个预设都会贡献一点,**白昼那一档就被两侧稀释了 —— 滑块正中间反而是最不像白昼的位置**。

数值量直接按 `n(a,b) = a + (b−a)·k` 插(`skyTime.ts:149`);颜色单独走一条:`new THREE.Color().setHex(x).lerp(new THREE.Color().setHex(y), k).getHex()`(`skyTime.ts:150-151`)。

`preset` 不是独立状态,是**推导出来的**(`skyTime.ts:315`、`:338-339`):

```ts
this._preset = u < 0.25 ? 'dawn' : u < 0.75 ? 'day' : 'dusk';     // skyTime.ts:339
```

`setPreset()` 只是 `setTimeOfDay()` 的一层糖(`skyTime.ts:320-321`):`dawn → 0`、`day → 0.5`、`dusk → 1`。

### 8.3 阴影相机参数必须由光源位置推导

SHADOW_FAR  = SUN_DISTANCE + 150   = 400      skyTime.ts:193

`skyTime.ts:183-190` 的注释记着这个坑:**曾经在这里写成 `far = 220`,比 `SUN_DISTANCE` 还小 30m**,阴影视锥在离场景 30m 的地方就截断了,**全画面一道影子都没有**。结论是"参数由光源位置推导,拆到两个文件里必然对不上"。

同理,`src/main.ts:155-159` 明确声明:**阴影相机的参数一律由 SkyTime 拥有,`main.ts` 不要再改**,并留下了诊断依据的位置(`screenshots/web/diag.json` 的 `lights[0].shadow`)。

### 8.4 PMREM 懒重建,以及 `environmentRevision` 这条注释

环境贴图**只在脏的时候重建**(`skyTime.ts:401` 的 `update()`),重建后把 `_envRevision++`(`:404`),并写回 `scene.environment` 与 `environmentIntensity = ENV_INTENSITY`(`:420`)。`ENV_INTENSITY = 0.10`(`:202`)—— 注释记载 0.35 会让画面发灰、盖过太阳。

const rt = this.pmrem.fromScene(this.pmremScene, 0, 1, SKY_SCALE * 2);

## 九、水面反射

`src/world/RiverReflector.ts` 725 行,文件头列了三个坑,每一个都是"不知道就会做错、做错了也不报错"的那一类。

### 9.1 为什么不用 `Water.js` / `Water2.js`

`RiverReflector.ts:10` 起。这两个 addon 的前提是"一整片无限大的水平面",而本作的河有**弯曲的岸线**、有宽度、有流向;水面几何是照着岸线切的,不是一块方形板。

### 9.2 三个坑

**坑一:法线是硬编码的局部 +Z。** `Reflector` 内部假定反射面法线是局部 `+Z`,所以它的平面默认是**竖着**的。补旋转有**两种补法,而错的那一种查不出来 —— 文件里称它为"本文件最贵的一课"**(`RiverReflector.ts:19-30`):

```
❌ 只补网格:reflector.rotation.x = -π/2
   → 反射数学正确,但网格的旋转连几何一起转,水面从躺着变成站着:
     实测世界包围盒 [16.5, 600, 0.06]、worldY = [-300, 300],
     河道成了一道 600 m 高的墙。
     而 localZWorld 报的仍是 (0,1,0) —— 一切正常。只查法线永远查不出这个错。

✅ 两段相消:几何烘 +π/2、网格转 −π/2
```

代码里这两处都能看到:网格旋转在 `:440`(`reflector.rotation.x = -Math.PI / 2;`);退化材质那一份在 `:525-526`。

**坑二:`options.shader` 是官方钩子。** 想改水面着色器不该去改 addon 源码,而应该通过构造参数传一份自己的 shader 进去 —— `RiverReflector.ts:427` 的 `new Reflector(surface, { shader: high, ... })`。

**坑三:反射 RT 里没有雾。** 反射是另起一次渲染画进 RT 的,那条路径不套场景雾。所以 `RiverReflector.ts` 在片元着色器里**手工把 exp2 雾重新实现了一遍**,每帧从 `scene.fog` 读参数写进 uniform(`:664-687`)。

### 9.3 量纲对齐:一段 400 倍的差距

这是水面看着像不像水的关键。RT 里保存的是**原始线性辐射**,量级在 10 左右;而受 sRGB 授权约束的基色量级是 0.023 —— **相差约 400 倍**。所以不能直接把 RT 采样混进基色。

`RiverReflector.ts:284` 的软压缩:

```glsl
refl = refl / ( 1.0 + refl * uReflCompress );
```

再叠一次散射混合(`:286-287`):`refl = mix(refl, refl * uScatter * 1.35, 0.45);`(注释:`1.35` 的上限是防它把暗部拉爆,`0.45` 是混合量)。

`RiverReflector.ts:281-283` 有一段边界声明值得原样保留:**这是量纲对齐,不是物理**。真实水面不会把白色船帆的倒影压暗,也不会把它染成土黄。本作品要的是"土黄、低饱和的内河",倒影是为这个观感服务的;这一点如实写在 `docs/08` 里。

`uReflCompress` 默认 1(`:379`)。这个值是用**剂量-响应实测**挑出来的(`:362-374`,探针是 `tools/perf/once/reflmix.mjs`,逐档截图一并留存):

| `uReflCompress` | 水面色相 H | 饱和度 S | 结论 |
| --- | --- | --- | --- |
| 0 | 216° | 0.18 | 天蓝 —— 即修复前的样子 |
| 0.5 | 31° | 0.10 | 色相对了但太灰,卡在判据 `S > 0.15` 之下 |
| **1** | **32°** | **0.19** | **采用** |
| 2 | 30° | 0.31 | 数字最好看,但见下 |
| 4 | 30° | 0.43 | —— |

**采用的不是数字最好看的那一档**(`:370-374`):`k = 2` 的 `S = 0.31` 离门槛最远,可逐档截图看下来,它把近处水面变成一大片没有内容的平涂土黄 —— 读起来是"泥滩"而不是"水",远处则压成一片灰白,桥的倒影糊掉。`k = 1` 的 `S` 只有 0.19、离门槛仅 0.04,但它保住了倒影里桥拱与栏杆的格眼,**一眼能看出这是水面**。注释写:

> 判据是**下限,不是目标**:一个能靠"把水调成泥"来满足的判据,满足了也不等于做对了。

这句被留在代码里,是为了防止后来者"只看着 S 往上调"。

### 9.4 `rtSize` 与 `everyNFrames` 是什么意思

`applyQuality(p)`(`RiverReflector.ts:644` 起)收到的是画质表里的 `reflector` 那一项,它做两件事:

- **`width` / `height`** → 反射 RT 的像素尺寸。真正落地在 `applyRtSize()`(`:590-600`),幂等,并且用 `Math.max(64, plan.width/height)` 兜底(`:592-593`);尺寸真变了还会置 `reflector.forceUpdate = true`(`:598`),否则第一帧显示的是上一档分辨率下的画面被拉伸。注释记了两个失败过的写法:关闭时跳过 resize 但 plan 已经推进;以及 low 档宽度填 0 导致 2×2 RT(见第 4.2 节)。
- **`everyNFrames`** → **每 N 帧才真正做一次反射 pass**。这是 `onBeforeRender` 外面包的一层节流(`:618-642`):

```ts
if (plan.everyNFrames > 1 && frameCounter % plan.everyNFrames !== 0) {
  skippedPasses++; frameCounter++; return;
}
frameCounter++; reflectionPasses++;
beginReflectionPass();
try { origOnBefore.call(...); } finally { endReflectionPass(); }
```

三个计数器(`reflectionPasses` / `skippedPasses` / `frameCounter`)让"节流到底有没有生效"成为一个可读的数。`try/finally` 保证 `endReflectionPass()` 一定配对执行,否则一次异常就会让 pass 计数永久错位。

`syncVisibility()`(`:602-616`)负责开关:`reflector.visible = on; flat.visible = !on; uReflMix = on ? 1 : 0;` —— 关掉反射时看到的是一片**退化材质**(`fallbackMaterial`,`:508-513`),不是空白。

那份材质的 `roughness` 必须接近 1(`:511-513`)。注释明确写着:不能用"水看着光溜"那个直觉给的 **0.42** —— `MeshStandardMaterial` 会吃 `scene.environment`(Sky.js 烘的 PMREM),0.42 时天空反射把基色压过去了,实测中景饱和度只有 S=0.03。这份材质观感明显不如反射版,注释把它标为**如实的设计取舍**:low 档与 A/B 对照组就用它,并且 A/B 报告里要写清。

### 9.5 反射层与诊断口径

`REFLECT_LAYER = 1`(`RiverReflector.ts:74`),用 `layers.enable()` 而不是 `set()`。`scanReflectLayer()`(`:483-500`)的策略是**默认开启、显式退出** —— 因为反射相机只看第 1 层的话会**丢掉所有灯光**(three 的 `pushLight` 在 `layers.test` 块内)和天空。

退出通道有两条:

- `userData.qm_reflect === 0` 的对象被跳过并计入 `excludedObjects`(`:487-490`)—— 这是粒子不进反射的第二道兜底(第一道是它进场太晚)。
- 扫描最后一句 `object.traverse((o) => o.layers.set(0))`(`:499`)。注释(`:495-498`)说明理由:上面那次遍历是"任何场景子节点都会被 `enable` 第 1 层",所以水面必须显式收口,**否则它会反射自己**(视觉上的无限递归);而且因为 `object` 是调用方加进场景的,这一步必须**跟着重扫走**,不能只在构造时做一次。

`diagnostics`(`:705`)里报的是 `enabled: reflectionOn()` 而**不是** `plan.enabled` —— 因为 `?reflect=0` 会覆盖 plan,报 plan 会误导。这个区别在 `:574` 那段注释里也点了名:`?q=high&reflect=0` 时 plan 报 high(`everyNFrames=1`),但实际一次反射都不会做。

## 十、人物

`src/actors/CharacterPool.ts` 739 行,里面几乎每一个常量后面都跟着"这个数是怎么量出来的"。

### 10.1 克隆的是骨架,不是网格

`SkeletonUtils.clone()`(`CharacterPool.ts:2`),而不是 `Object3D.clone()`。理由写在 `:26-28`:后者会**共享 Skeleton**,48 个人共用一个骨架、动作完全同步(计划书风险 #3)。

材质必须**逐个 `clone()`**(`:410`):网格可以共享几何,但材质要被单独染色(见 10.4)。

### 10.2 位置用 `+=`,不用 `set()`

模板 rig 自己带着一个**烘进 `position.y` 的落地修正量**(文件头 `:30-32` 起),所以设定位置时必须用 `+=` 叠在模板的基准上,直接 `set()` 会把那个修正量抹掉。

### 10.3 朝向是量出来的,不是假设的

- `measureFacingFrom` **必须用髋,不能用脚**(`:206-212`)。注释记载:最初写的是"优先用 `foot_L/foot_R`",量出来是 **155.0°** —— `carry` 是一具**迈步中的**姿态,两只脚一前一后,连线表示的是"这个人在迈哪条腿"而不是"身体朝向";而走路姿态的脚**永远是错开的**,这个偏差不会自己消失。取不到髋才退回膝、脚(`:262-267`)。
- `measureArmFacing` 用 `upperarm_L/R`,因为 `shoulder_L/R` **完全重合**(实测偏差 0.0000m,`:293`)。它的**能力边界**也写在接口注释里(`:87-93`):它与 `bodyFwd` 同公式,所以**公式整体反号时两者会一起反**,夹角仍是 0° —— 要发现"整体反了"必须靠位移。
- `WANT_YAW_OFFSET = Math.PI`(`:359`)。依据是 Blender 侧 `08_assembly.py` 里人的前向定义(引用在 `:340-342`)。这段注释记着一个**两个 180° 互相抵消**的故事(`:344-354`):旧代码写的是"角度相减",而 `facingYaw = atan2(0,−1) = π`,于是 yaw=0 时反而转 −180°,整套人正好朝反方向走。它**之所以一直看着没出错**,是因为转身那段同时也在错误地转 180°(见 10.4),两个 180° 抵消,人恰好走对了方向 —— 代价是加载后所有人先原地自转半圈。修掉自转之后抵消没有了,才暴露出真正的口径错误。

### 10.4 染色与 `curYaw`

`tintRobe()`(`:417`)用 `mulberry32(hashId(id))` 做确定性伪随机,对每件袍子做 ±18% 亮度、±8% 每通道的扰动 —— 同一个 id 每次跑出来的颜色一样,截图可复现;色值还会写回 `userData.qm_robe`(`:457-458`),让诊断脚本能读到它而不是去猜。

`curYaw` 上挂着一段**已记录的缺陷**(`:136-146`,修复处 `:557-565`):转身差曾经写成 `diff = it.yaw - it.rig.rotation.y`。但模型的 `rotation.y = yaw − 180°`(实测 `facingYaw = π`,模型脸朝 −Z),于是**每帧都读到 180° 的误差**,命令一直存在 —— 48 具里有 **25 具**在加载后以 2.6 rad/s(**约 149°/s**)原地自转半圈。

它为什么难发现,注释写得很清楚(`:143-145`):**自转会把"朝向"和"前进方向"一起带走**,所以"朝向 vs 位移"的自检读到的是 0° —— 两边一起错,自检反而通过。只有把"目标 − 实际"这个**原始读数**印出来才看得见(实测 p50 = 179.3°)。

现在改成减**自己记的 `curYaw`**,与 `it.yaw` 同口径。

其他常量:`BODY_RADIUS = 0.28`(`:168`)、`TURN_RATE = 2.6`(`:170`)。

### 10.5 地面采样节流

`GROUND_RESAMPLE = 0.15`(`:189`)。这个值是被性能逼出来的,注释里有一张实测表(`:172-188`):

| 步长 | p50 | p95 | max | 最差(虹桥) |
| --- | --- | --- | --- | --- |
| 0.30m | 0.0003 | 0.050 | 0.141 | 0.183 |
| 0.15m | 0.0003 | 0.024 | 0.052 | 0.086 |

而节流的必要性来自 `:613-621`:射线用的是 `groundAt` 内部的 `intersectObjects`,**实测单次 p50 = 0.595ms**;场上 37 个走动的人 × 0.595 ≈ **22ms/帧,占一帧的 85%**,比渲染的 3.9ms 高一个量级。

这里还记着一个"注释与代码不符"的事故:**0.30m 的节流当时只卡在赋值高度那一行上,射线照打** —— 注释写着"每移动 0.3 米采一次",而代码每帧每人采一次。现在节流判据卡的是**射线本身**(`:151-153`),并且记的是**采样点**而不是当前位置(`:638`)。

`snapshot()`(`:63`)返回的每条记录里带 `yawDeg` / `curYawDeg` / `turnDiffDeg` / `bodyFwd` / `armFwd` / `baseOffsetY` / `grounded` —— 这些字段的存在理由是让"朝向对不对""脚有没有离地"成为可断言的值,而不是靠看图。

### 10.6 步态

`src/actors/proceduralWalk.ts`:**不用 `AnimationMixer`**,直接在每帧算骨骼旋转。

- 一律 `copy(rest).multiply(delta)`(`:188`),而不是 `rotation.x +=`。注释(`:13`):累加写法跑够几十秒就拧成麻花。
- 摆动轴**从骨架推导**,不是世界 Y(`:110` 起的"侧向轴"一段)。
- 相位**由距离驱动**(`:179`):`phase += (speed * dt) / STEP_LENGTH * Math.PI`。按距离而不是按时间,人走得快慢与步频自动一致。
- 振幅:`THIGH 0.42` / `KNEE 0.55` / `ANKLE 0.18` / `UPPERARM 0.30` / `FOREARM 0.20`(`:47-51`);`STEP_LENGTH = 0.75`(`:54`)。
- 膝盖用 `halfWave`(`:186`):`Math.max(0, Math.sin(a))`,保证**膝盖只会往后弯**。
- `baseBoneName` 去掉 `_<n>` 后缀(`:95`)。实测骨骼名统计 `{"0":37,"6":11}` —— 仅靠 `root` 这个名字就恢复了 37 个角色的骨骼。

### 12.3 缓动为什么自己写

`src/camera/tween.ts:4-9` 记了不用 GSAP 的理由:**GSAP 是"专有但免费"(not OSI-approved),授权可由一方单方终止**,而本项目要求依赖全部免费且可本地运行。顺带还有个好处,就写在下一段:缓动曲线的数学性质由自己保证,"无弹跳"这个验收条件**可以从导数推出来**,不必靠眼睛看。

缓动函数是解析式:

```
easeCamera(t) = 1 − (1−t)⁴(1 + 4t)          tween.ts:52
easeCameraDerivative(t) = 20t(1−t)³          tween.ts:59
```

**无反弹是可证的**:`f'(t) = 20t(1−t)³ ≥ 0` 在 `t ∈ [0,1]` 上恒成立,所以位置单调,不会冲过头再弹回来。

时长按距离缩放(`:75-77`):`k = sqrt(max(d,0) / TWEEN_REF_DIST)`,`duration = clamp(TWEEN_MAX_SEC · k, TWEEN_MIN_SEC, TWEEN_MAX_SEC)`,其中 `TWEEN_MIN_SEC = 0.9`、`TWEEN_MAX_SEC = 1.8`、`TWEEN_REF_DIST = 36`(注释:走这么远正好用满上限)。

> **一处注释与常数对不上,以代码为准。** `tween.ts:66-68` 的举例写「36m 的切换 1.8s,9m 的切换 1.35s」。按 `:76-77` 的公式代入 `d = 9`: `k = sqrt(9/36) = 0.5`,`1.8 × 0.5 = 0.9`,再被 `TWEEN_MIN_SEC = 0.9` 夹住,结果是 **0.9 s,不是 1.35 s**(要得到 1.35 s 需要 `TWEEN_MAX_SEC = 2.7`)。举例值不参与任何计算,所以这不影响行为,但它是"注释里的数也要复算一遍"的又一个样本。本文正文一律用公式,不用这个举例。

`update()` 里,**位置与目标点用同一个缓动后的 `k`**(`:128-131`)。注释写明理由:两边各用一条曲线,或者一边缓动一边不缓动,都会让视线在中途偏摆一下,看上去像机身在扭。完成时直接给**精确**的终点值而不是浮点余量(`:133-135`)—— 验收要求"结束位置误差 < 0.05m",给精确值最省事,也免得多一帧的差。

## 十三、状态与 URL

### 13.1 `store.ts`

**单一真相源**(`src/ui/store.ts:2`)。三条约定写在文件头(`:4-7`):任何模块都只能**读** `store.read()`;唯一的写入口是 `ui/actions.ts` 里的 action;UI 组件只调 action,不直接改状态。

文件头还解释了这条约定为什么不是洁癖(`:9-11`):**画质切换要保证"对象 UUID 集合不变",切换时辰要保证"PMREM 重建但相机不动"**。如果谁都能改状态,这些不变量就无法断言,`tests/state_invariants.mjs` 也就没有拦截能力。

`write()`(`:209-213`)在通知之前先 `Object.freeze(next)`,状态对象在写入后即被冻结;`write` 的文档注释点名了它的用途:**仅供 `ui/actions.ts` 调用**。

初始值(`initialState()`,`:153`):`quality: 'mid'`(`:182`)、`tod: 0.5`(`:183`,即白昼)、`ui.anim = true`(`:171`)。

### 13.2 `subscribe()` 会**立即同步推送当前值** —— 以及它造成的真实缺陷

```ts
subscribe(fn: Listener): () => void {
  this.listeners.add(fn);
  // 立即推一次当前值,订阅者不必自己再读一遍
  fn(this.state);
  return () => this.listeners.delete(fn);
}
```

`src/ui/store.ts:196-201`。

"立即推一次"这个设计本身是合理的:订阅者不用自己再读一遍,也不会漏掉订阅之前发生的最后一次变更。

**但它对订阅者的写法有硬性要求:回调里的"变了才做某事"守卫,其追踪值的初值不能读当前状态。** 因为回调会**同步**跑一次,而那次跑的时候状态可能已经被别人改过了。

这个要求没有被满足,后果记在 `src/main.ts:319-345` —— 见下一节。

### 13.3 URL 参数

`src/core/urlState.ts`。`UrlState` 接口(`:23-38`):

| URL 参数 | 对应字段 | 类型 | 性质 |
| --- | --- | --- | --- |
| `spot` | `spot` | 景点 id | 状态 |
| `tod` | `tod` | 0..1 | 状态 |
| **`q`** | `quality` | `low\|mid\|high` | 状态 |
| `tags` | `tags` | bool | 状态 |
| `hud` | `hud` | bool | 状态 |
| `wire` | `wire` | bool | 状态 |
| `cam` / `look` | 同名 | 三维坐标 | **测量参数** |
| `reflect` | `reflect` | bool | **测量参数** |

⚠️ 注意**画质的网址参数是 `q` 而不是 `quality`**(读:`urlState.ts:66`;写:`:107`),字段名才叫 `quality`。

文件头说明了两条用途,以及第二条才是真正的原因(批量截图不必模拟点击,`urlState.ts:1-19`)。`cam` / `look` 直接指定机位;`reflect` 强制开关水面反射。这两个的注释都强调:**它们不是用户状态,是"这一次怎么量"**。

读取侧(`readUrlState`,`:61-81`):

- `bool()`(`:54-59`)只认 `'1'|'true'` → true、`'0'|'false'` → false,**其余一律 null**(不是 false)。
- `vec3()`(`:42`)对解析不了的输入**发警告**,而不是静默忽略。
- `tod` 先转数,`Number.isFinite` 不成立就是 `null`(所以 `?tod=abc` 是"没给"而不是"给了一个坏值");给得出数时再钳到 `[0,1]`(`:64-65`、`:72`)。
- 无法识别的 `q` 会 `console.warn` 并当作没给(`:67-68`)。

写回侧(`writeUrlState`,`:98-118`):

- 用 `replaceState` 而不是 `pushState`(`:86-87` 说明:用 push 的话每切一次景点就多一条历史记录)。
- 空值走 `delete` 而不是写个空串(`:100-103`),所以"没给"与"给了 0"在地址栏里可以分开。
- `tod` 写回时固定两位小数(`:106`),布尔写回成 `'1'`/`'0'`(`:108-110`)。
- `cam` / `look` / `reflect` 在写回时被**有意丢弃**(`:112-114`)。注释(`:92-95`)诚实地标注了代价:**用户手动把画质切到 high 之后,URL 里原来的 `reflect=0` 已经没了,画面会变成有反射**。

在 `main.ts` 里,`cam` + `look` **优先于** `spot`(`src/main.ts:90-104`);未知的 `spot` id 会**抛异常**而不是退回默认机位。

### 13.4 那三个哨兵值

这是 `src/main.ts` 最重要的一段,原文在 `:319-345`。

问题链条是这样的(顺序很关键):

1. URL 状态在这一段**之前**就已经写进 store 了(`main.ts:113-152`,那段自己也有一个长注释,见下)。
2. `store.subscribe()` 会**立即同步推一次当前值**(`store.ts:199`)。
3. 如果守卫写成:

```ts
let lastTod = store.read().tod;         // ← 错误写法
...
store.subscribe((s) => {
  if (s.tod !== lastTod) { lastTod = s.tod; skyTime.setTimeOfDay(s.tod); }
});
```

那么首次推送时 `s.tod` 与 `lastTod` 是**同一个值**,`!==` 恒为**假**,setter **一次都不会被调用**。

后果不是"少调一次",而是:**`?tod=` 与 `?wire=` 这两个网址参数从来没有生效过**。`store.tod` 里明明写着 0.2,太阳却一直停在 day 预设上(`setPreset('day')` 是 `SkyTime` 构造函数的最后一件事,`skyTime.ts:287`)。而且**任何"查 store"的断言都会通过** —— 状态对了,渲染没动。

正确写法是取一个"真实状态不可能等于"的哨兵:

```ts
let lastTod = Number.NaN;          // tod 恒在 [0,1] 之间,NaN 安全
let lastQuality: Quality | null = null;   // 画质是三选一的字符串
let lastWire: boolean | null = null;      // 线框是布尔
```

`src/main.ts:343-345`。多出来的那一次调用是幂等的:`setTimeOfDay` 只是重设一组参数并标脏一次 PMREM,`setWireframe` 把材质设成本来就是的值。

**这段注释自己记下了它是被预言过的**(`main.ts:333-336`):`src/world/skyTime.ts` 的 `environmentRevision` 注释里一字不差地写过"只断言 `store.tod` 变了,证明的只是状态改了,完全没碰渲染侧"。当时没人顺着这句话去查这条接线。

同一段注释还记了一个更早、更严重的事故(`main.ts:115-126`):**URL → store 这一段曾经整个不存在**。`readUrlState()` 一直在解析 `tod / q / tags / hud / wire`,但没有任何地方消费它们,返回值被读出来就丢掉了。于是**所有带 `?q=high` 的截图其实都拍在默认的 mid 档上**,而截图工具记录的 `url` 字段里明明写着 `q=high`,看报告的人(包括作者自己)会认为那是 high 档的图。注释里那句话值得抄在这里:

> 一个"读数与实际不符"的仪表比没有仪表更坏。

现在这一段必须走 `ui/actions.ts` 的 action 而不是直接改 store:store 是唯一真相源,action 是唯一写入口,绕过去的话 UI 的高亮状态不会跟着变。

最后,应用完参数会打**一行汇总**而不是每个参数各打一行(`main.ts:149-151`):探针脚本要靠这行确认参数真的落地了。没有这行的话,`?q=high` 没生效也只是"图看着还行"。

## 十四、资产加载

### 14.1 进度预算

`src/core/assets.ts:57-65`:

```
W_MANIFEST = 0.02   读清单
W_FETCH    = 0.73   下载
W_PARSE    = 0.22   解析
W_COMPILE  = 0.03   编译着色器
T0 = 0, T1 = 0.02, T2 = 0.75, T3 = 0.97
```

**为什么自己写 fetch 而不用 `GLTFLoader.load()`**(`assets.ts:4-9`):`GLTFLoader.load()` 的 `onProgress` 依赖响应的 `Content-Length`。静态服务器若用了 chunked 编码或 gzip 动态压缩,就没有 `Content-Length`,**进度会一直停在 0 然后突然跳到 1**。本作品把每块的字节数写进了 manifest,自己按 `ReadableStream` 累计,分母就与服务器行为无关了。这就是 `assetUrl()` 之外 `fetchArrayBuffer()`(`:91-130`)存在的理由;没有 `Content-Length` 时它降级为一次性读取。

**最后一段不能省**(`assets.ts:17-18`):`compileAsync` 不是"等待",而是**真正会卡住主线程**的一步。把它算进进度,进度条才不会在 97% 处凭空停住几秒然后突然完成。

进度回调在 `:214`、`:221`、`:239`、`:270` 逐段推进。

**进度条之外,还有一份阶段变迁记录**(`src/ui/store.ts:37-62`)。`PhaseMark { phase, t, progress }` 按发生顺序存进 `loadState.phaseLog`,`t` 取 `performance.now()`(`store.ts:37` 的注释:与主循环同源)。为什么要留这份看起来像调试残留的东西,`store.ts:57-60` 写得很直接:

> 本机 1MB 的 GLB 走 localhost 只要十几毫秒,外部脚本按 50ms 轮询根本采不到 fetching / parsing —— "进度确实依次经过了下载、解析、编译"这条出口断言,只能靠**在应用内部记录变迁**来证明,靠轮询是证明不了的。

这条和 §13.4 的哨兵值是同一类:断言通过不等于事实成立。一个败在采不到过程(轮询采样间隔比过程的历时还长),一个败在判据从一开始就不可能成立(守卫拿已被覆盖的值当基准)。两次都不是"实现错了",是**验证方法本身没有分辨力**。

### 14.2 `assetUrl()` 与相对路径

```ts
function assetUrl(rel: string): string {
  // 相对 document.baseURI 解析:这样 dev(/)与 dist(./)以及
  // 部署在任意子路径下都能取到,不需要构建期注入 base。
  return new URL(rel, document.baseURI).href;
}
```

`src/core/assets.ts:67-71`。

相对 `document.baseURI` 解析(而非相对 `location.href`,也不是拼一个绝对前缀)是**离线部署**的前提:同一份构建产物放在站点根、放在 `/foo/bar/` 下,资源路径都成立,不需要构建期往代码里注入 base。这是代码注释自己写下的理由(`assets.ts:68-70`)。

> 未验证:构建期实际使用的 `base` 取值、以及 `file://` 打开是否成立,本次没有查 `vite.config.ts` 也没有实测,故不写。

### 14.3 `parseGlb()` 里必须关掉 `vertexColors`

`src/core/assets.ts:144-155` 的注释:**r186 的 GLTFLoader 只要发现 `COLOR_0`,就会把 `material.vertexColors` 设成 true**。而本作的 `COLOR_0` 装的是风动的**权重**(见 `src/actors/propsAnim.ts` 文件头关于 `qm_flex` 的说明),不是颜色。不关掉的话,权重会被当成颜色乘进基色里去。

顺带在解析时给每个网格设 `castShadow = true` / `receiveShadow = true`。

### 14.4 失败返回 `null`,不抛

`loadAssets()`(`:184` 起)失败时**返回 `null`** 而不是抛异常(`:201`、`:229`、`:244`)。理由:`main.ts` 的 `boot()` 拿到 `null` 就直接 return(`main.ts:620-621`,`if (!assets) return; // 失败信息已经写进 store,遮罩会显示`),失败信息已经写进 store,遮罩会把它显示给用户。

失败信息的结构是 `LoadFailure`(`src/ui/store.ts:29-35`):`url`、`stage: 'manifest' | 'fetch' | 'parse' | 'compile'`、`status?`、`message`。`:31` 的注释解释了为什么 `stage` 必须存在 —— 「遮罩上要显示它,否则用户只知道"失败了"」。抛异常的话这四样会散在控制台里,遮罩只剩一句"加载失败"。

`warmUp()`(`:258-272`)里的 `compileAsync` 失败**不致命**:`console.warn` 之后退回首帧同步编译(`:268`)。
