# 03 · 模型重建:从原画到 GLB

本文写的是**模型是怎么来的**:从 `blender/config.py` 里那一串数字,到 `public/models/` 下的四个 GLB。

它不重复 `docs/09-资产统计.md` 的表。面数、字节、材质数、贴图数、骨架表、`qm_kind`/`qm_zone` 分布,一律以 `docs/09` 与 `public/models/manifest.json` 的**真实读数**为准 —— 本文只在需要说明"为什么会是这个数"时才引一两个总数,并在引用的地方写明出处。

三条纪律,先写在前面:

1. **本文的每条陈述都追到 file:line。** 追不到的,写「未验证」或者不写。
2. **不出现"完美还原""考古级精度"这类结论。** 事实上 `blender/config.py:21-22` 自己写着:**不得**据此宣称"考古级复原"或"精确还原"。本文服从这条。
3. 代码与本文冲突时,**以代码为准**。

## 1. `config.py`:唯一真相源

### 1.1 为什么只留一个文件

`blender/config.py:1-5` 的第一句话就是定位:

> 尺寸与参数的**唯一真相源**。`build/` 下的脚本只从这里取数,`tasks/validate_scale.py` 也只对照这里断言。改尺寸只改这一个文件。

这条纪律不是洁癖,是被具体故障逼出来的。配置里有两处注释记录了代价:

- `config.py:446-449`(彩楼欢门的构造参数):这些数由 `build/05_celebrations.py` 与 `tasks/validate_scale.py` **共读一份**。若两处各写一份,"改了一处就会让校验器按旧参数去核对新几何,得出的失败与几何无关"。
- `config.py:641-645`(`Human` 为什么单独开一个类):因为它是**量别人的尺子** —— 幌子下缘、门洞、栏杆、船舱的判据都要拿它去比。"一旦有两处各写各的 1.70/1.75,就会有一处先改、另一处悄悄过期,而两处都'看着像那么回事'。"

于是 `Human.STATURE = 1.70`(`config.py:656`)与 `Character` 里那一整套比例(`config.py:692` 起,`S = Human.STATURE`)是**尺子**与**身体**的分工:改 `STATURE` 一处,全身跟着变(`config.py:668-676`)。

### 1.3 可靠性标注:是注释,不是字段

`config.py:15-19` 声明每个常量都带 `Reliability` 标注,并给出三档定义:

```
A —— 有文献或实物旁证,可较有信心
B —— 由 A 级尺寸推算得来,误差随推算层数放大
C —— 为观感或工程可行性选定,无考据支撑
```

`Reliability` 枚举也确实定义了(`config.py:45-50`),docstring 里说它"写进统计报告,也写进文档"(`config.py:46`)。

**但实际用起来是注释、不是字段。** 全仓库检索 `Reliability.` 的结果:除了枚举自身定义,没有任何一处把 `Reliability.A/B/C` 赋给某个常量;实际写法是散文注释,例如:

- `config.py:80-82` `SPAN`/`RISE`/`DECK_WIDTH` 各带一行 `# ... Reliability B`
- `config.py:135-136` `SYS1_DEPTH`/`SYS1_WIDTH` `# ... Reliability C`
- `config.py:442` `Celebration.COUNT = 7  # Reliability B`
- `06_props.py:22-23` 柳树"存在性 A 级 / 尺寸全 C 级"
- `00_layout.py:19`、`02_river.py:69,312`、`03_boats.py:54,61`、`05_celebrations.py:14,130` 同类散文标注

这与 `docs/08-已知局限与未做还原.md` 里记的"`reliability` 作为结构化字段从未实现"是同一条事实。**本文不把它写成"结构化元数据"。**

### 1.4 尺寸链的根,与一条被证伪的数据

`config.py:7-13` 是全文件最重要的一段坦白:

> 下表里的尺寸**不是考古测绘成果**。张择端原画没有比例尺,这些数字来自后世研究者(主要是唐寰澄《中国木拱桥》)基于"虹桥栏柱间距约 1m"这一单点假定做的**链式推算**。也就是说:1m 是整套尺寸链的根节点 —— 它若错了,下游所有尺寸等比地错。

并且明确:**不得**据此宣称"考古级复原"或"精确还原"(`config.py:21-22`)。

`config.py:24-27` 另外记了一条**禁止使用的数据**:百度百科称虹桥"跨度约 5.28 米";528.7cm 是**全卷长度**,不是桥跨。任何脚本都不得引用该值。

这就是为什么 `Bridge.SPAN = 20.0` 是 B 级而不是 A 级 —— 它是从那个单点根节点推出来的,而 `RAIL_POST_SPACING = 1.0`(`config.py:168`)本身也标着 C 级并附说明。

### 1.5 尺寸链上的自洽检查:导入即自检

`config.py:1638-1643` 说明 `_self_check()` 的用意:导入本模块时立刻跑一遍关键不等式,"尺寸链一旦被改错,应该在这里就炸掉,而不是等到渲染出一座形制错误的桥"。它在文件末尾被无条件调用(`config.py:1736`)。

这构成尺度的**第一层**校验(另两层见 §5)。它检查的是**配置内部**的不等式,不碰几何。

一个具体例子能说明这类不等式为什么非有不可:`config.py:100-105`(通航净空 `CLEARANCE_MIN = 4.30`)记着,原计划里"拱矢 5.0 + 净空 ≥5.0"是**互相矛盾**的 —— 拱矢 5.0 的桥不可能有 5.0 的净空。于是净空不写成常量,写成算法 `clearance_actual()`(`config.py:106`)= `RISE − |SYS1_RADIAL_OFFSET| − SYS1_DEPTH/2`,并留出 0.21m 余量;`config.py:100` 明说这个余量"偏紧是有意的",因为拱骨截面是 C 级。

### 1.6 写死在配置里的"形制红线"

配置里有一部分常量不是尺寸,是**约束**。它们的存在方式是"写死 + 由校验器断言":

- **屋面形制白名单** `Building.ROOF_WHITELIST = ("wudian","xieshan","xuanshan")`,`ROOF_FORBIDDEN = ("yingshan",)`(`config.py:418-419`)。理由在 `config.py:410-415`:北宋**尚无硬山顶**,硬山顶明代才随砖砌山墙普及;"出现 yingshan 即判定形制错误,validate_scale.py 会拒绝产出"。
- **彩楼欢门不用斗拱、用绳绑** `Celebration.HAS_DOUGONG = False`、`BINDING = "rope"`(`config.py:443-444`),由 `validate_scale.celebration.binding` 断言。
- **虹桥无榫卯、无铁钉** —— 这条不写在常量里,写在 `build/01_bridge.py:20-23`:北宋虹桥原构是捆扎做法,榫卯是南渡之后闽浙廊桥的演进形态;"参考文章里要求做榫卯,本作品**不做**,因为做了反而破坏宋代感"。
- **眠桅过桥的硬上限** `Boat.DRAFT_MAX = 1.28`、`AIR_MAX = 4.00`(`config.py:369-370`),`build/03_boats.py:12-14` 说明它们"不是'看着差不多',是 validate_scale.py 里的硬断言"。

## 2. `run_all.py`:顺序、门禁与退出码

`blender/run_all.py` 是总控。它做四件事:跑 builder、跑形制校验、写场景统计、导出。

### 2.1 `STAGE_BUILDS` 就是"这一阶段"的定义

```python
STAGE_BUILDS = {
    "1": ("01_bridge",),
    "2": ("00_layout", "01_bridge", "02_river", "03_boats",
          "04_buildings", "05_celebrations", "06_props",
          "07_characters", "08_assembly"),
}
```
(`run_all.py:62-75`)

**缺 builder 是失败,不是提示。** `run_all.py:166-182` 用一整段注释记了原因:上一轮这里只打一行 `⚠ 以下 builder 尚不存在`,然后照常导出、照常 `return 0`;于是日志末尾同时出现"完成。7 个 builder 跑过"和"没有执行:07_characters, 08_assembly",而退出码是 0。作者据此把那次运行复述成"阶段 2d 门禁全绿",因为**读的是退出码与通过计数,不是日志末尾**。

现在的判据改成:`run_all.py:179-182` —— "`STAGE_BUILDS` 是这一阶段的定义。它声明了 9 个 builder,就只有 9 个都跑过才叫跑完这一阶段。缺一个就不导出、返回非零。想少跑一个,去改 `STAGE_BUILDS` —— 那样缺失会变成一次**显式的编辑**,而不是一次静默的跳过。"

### 2.2 三道门禁的执行顺序

`main()` 的顺序是固定的(`run_all.py:147-287`):

1. **跑 builder**(`run_all.py:164`)。缺件时打印警告,但**不立刻返回** —— 见 `run_all.py:183-189` 与 `run_all.py:234-235`:校验报告"该说的都说了 —— 现在才拦。放在 validate 之后是为了不浪费这一次运行给出的信息"。
2. **形制校验** `run_validate(stage, strict)`(`run_all.py:207-208`)。`AssertionError` → 打印后 `return 1`,**不导出**(`run_all.py:209-213`)。校验脚本自身抛异常同样是失败(`run_all.py:214-226`),理由写在 `run_all.py:220-221`:"校验器崩了却读不到原因,比校验器不报错更坏 —— 后者我知道自己不知道,前者会让我以为已经看过了。"校验脚本不存在时返回 `"missing"` 而**不是** `"pass"`(`run_all.py:131-132`),并打印"本次产物**未经过形制校验**"( `run_all.py:228-230`)。
3. **缺件拦截**(`run_all.py:236-242`):到这一步才因为缺 builder 中止,并明确"已在导出前中止,`public/models/` 未被本次运行改写"。
4. **场景统计** `report_objects.report()`(`run_all.py:257-258`),**放在导出之前**。理由在 `run_all.py:244-252`:① 导出崩在半路时 stats.json 已经写出来了,那时它是唯一能说明"场景到底建成了什么样"的东西;② 导出器会自己动选择集与依赖图,让报告描述"建出来的场景"而不是"导出器动过之后的场景",边界才干净。代价也写明了:它不能用来证明"导出的内容就是这个数"—— 那件事由 GLB 侧的 `tools/lib/glb.mjs` 单独量,两份摆在一起比。
5. **集合声明门禁**:阶段 ≥2 时调 `report_mod.assert_declared_collections(stats_data)`(`run_all.py:261-262`)。
6. **导出** `MOD.load_build("09_export").run()`(`run_all.py:279-280`)。

### 2.3 `exit 0` 本身撒过谎

`run_all.py:290-307` 的 `_exit()` 必须用 `os._exit(code)` 而不是 `raise SystemExit`:

> 实测:脚本抛异常时 Blender 的 `--python` 处理器会把异常吞掉,**进程仍然返回 0**。于是"构建崩了"和"构建成功"在调用方看来一模一样 —— 我据此写下"exit 0,46 通过"这类结论,而实际上那一次跑到了一半就炸了。

代价也写明:不跑 atexit、不刷缓冲区,所以必须先自己 flush,否则日志会丢掉最后一段(包括 traceback)。

## 3. 十个 builder:各自造什么

顺序即 `STAGE_BUILDS["2"]` 的顺序(`run_all.py:64-74`),也是文件名的顺序。每个 builder 的职责,取自各文件**文件头注释**。

### `00_layout` —— 场地底面(`blender/build/00_layout.py`,399 行)

两岸地坪、沿河街道、纤道、桥头引道、远景地裙(`00_layout.py:2`)。它是"整个场景的底面",自己不好看,但"是后面八个 builder 的公共参照:所有物体都'站'在它上面,坐标全部来自 `config.Site`"(`00_layout.py:4-6`)。

平面分区(`00_layout.py:16-17`):东岸 `水面 | 收分 | 纤道 | 街道 | 市井地坪 | 城墙 | 郊野`,`x = 0 / 8.25 / 10 / 12.2 / 21.2 / 58 / 76.4 / 108`。

两处明写的推定(`00_layout.py:19-26`):街道贴河布置、宽 9m,取这个数是"为了让两辆独轮车 + 一行人能错身而过 —— 这是**功能推定**";郊野地面起伏 ±1.2m,用**固定相位的正弦叠加**生成而不用 `mathutils.noise`,理由是"避免 Blender 版本间噪声实现漂移导致两次构建立不了等价"。

边界:`00_layout.py:28` —— 本 builder **不建水面、不建河床**,那是 `02_river` 的事。

### `01_bridge` —— 汴河虹桥(`blender/build/01_bridge.py`,510 行)

形制依据是《东京梦华录》"其桥无柱,皆以巨木虚架,饰以丹雘,宛如飞虹"(`01_bridge.py:6`):「无柱」→ 没有桥墩;「巨木虚架」→ 编木(贯木)拱。

结构是两个独立的折线拱系统互相搭置,各自都不稳定,合起来才成拱(`01_bridge.py:12-18`):

- 第一系统 **10 组,每组 3 根等长拱骨**(共 30 根);
- 第二系统 **11 组,每组 2 长 2 短共 4 根**(共 44 根);
- "两系统的节点**互相错开半个组**,所以一者的节点正落在另一者构件的跨中,形成'你压我、我托你'的互相支承。"

**已知简化,该文件自己写在最前面**(`01_bridge.py:25-33`):真实的贯木拱,两系统在同一弧面上**逐点上下穿插**,正是这种交错把两个系统互相锁死;本模型把两系统做成**同心的内外两层**折线拱(偏心量见 `config.Bridge.SYS1/2_RADIAL_OFFSET`),在跨中呈嵌套关系,**只在两端起拱处真实交叉**。"这是为控制几何复杂度做的简化 —— 结构原理、构件数、无榫无钉、索绑这些**形制红线都保留了**,但'逐点穿插'的编织细节没有还原。"

**索绑是分层的**(v2 起,`01_bridge.py:35-38`):第一系统的节点捆第一系统、第二系统的节点捆第二系统,各捆各的一层。理由:"真实虹桥的两系统是**互相支承**关系,并不存在一根绳子把两层一起箍住的做法 —— v1 那样做,渲染出来是一串挂在拱上的大铁圈。"

### `02_river` —— 水、河床、驳岸、木桩、踏步(`blender/build/02_river.py`,353 行)

四样东西(`02_river.py:12-15`):水面 `z = 0, x ∈ ±8.25`;河床 `z = −1.5`(淤泥);驳岸自水边斜收到河底外加压顶石;附件为入水木桩与踏步。"河道断面沿 Y 恒定,所以整条河是**一次放样**扫出来的,不是逐段摆"(`02_river.py:17`)。

这个文件有一段专讲**水色**(`02_river.py:19-27`):汴河是黄河冲积平原上的浑水河,水色是土黄带绿;"任何'标准水面着色器'(three.js 的 Water.js 之类)都会给出蔚蓝的地中海,因为那些着色器把散射色写死成青蓝"。所以 `config.Palette` 里显式写了 `WATER_DEEP / SHALLOW / SCATTER`,网页侧必须喂这三个值,阶段 4 会用截图采样断言河道中心像素色相落在 25–45°。该文件只负责几何 —— 但这里生成的 `qm_id=river_surface` 就是那三个值的落点。

边界:河道断面沿 Y 恒定意味着**河床是平的**,这是几何上的简化,不是考据结论。

### `03_boats` —— 漕船与船队(`blender/build/03_boats.py`,1341 行)

船壳、拱形舱篷、人字桅(可眠)、橹、招、舵,以及一支船队(`03_boats.py:2`)。

这个 builder 存在的意义,**不是"河上要有船"**,而是让**眠桅过桥**在几何上真的成立(`03_boats.py:9-14`):船必须真的浮在 `z = 0` 的水面上,吃水不能超过上限;眠桅之后的总高必须真的低于拱桥净空,否则桅杆会穿桥。"这两条不是'看着差不多',是 validate_scale.py 里的硬断言。"

`03_boats.py:21-22` 明确:"本文件刻意不写'完美还原'。哪些是从原画读出来的、哪些是推定,逐条记在下面的 §推定 一节。"

坐标约定在 `03_boats.py:24-28` 起:每一条船先在自己的**局部坐标系**里建好再整体摆到世界里;`x` 横向(0 为中纵剖面,± 为左右舷),`+Y` 为船头方向,`z = 0` 在满载水线。这个约定是后面"回读复核"能成立的前提。

文件头还记了一处**空间上的矛盾及其解法**(`03_boats.py:42-50`):桅与舱篷在几何上会打架。原画里解掉它的办法是 —— **舱篷不在桅座底下**:桅立在船中之前的工作面上,篷压在它后面的货舱上,桅倒下来正好从篷首面上掠过去。所以本文件把"篷首面必须在桅座之后 `COVER_CLEAR` 以上"写成一条**计算出来的硬约束**,而不是挑几个看着顺眼的坐标。理由:"挑坐标的写法在这次返工里已经吃过一次亏:桅座、篷首、眠桅架三者的位置互相牵制,动一个另两个就悄悄穿模,而穿模在渲染图上**看起来像材质问题**。"

同文件按可靠性分了组的推定清单(`03_boats.py:52-69`):

- **Reliability B**(有原画与文献支撑,细节靠推定):船壳按漕船的"肥首肥尾"取形(漕船是载货船,首尾不收得像渔船那样尖,中段平直、两端用 smoothstep 收);拱形舱篷压在货舱上、首尾留出工作面;人字桅两腿跨舷立于甲板,眠桅时桅身**倒向船尾**,搁在艉部的眠桅架上。

### `07_characters` —— 蒙皮人物模板(`blender/build/07_characters.py`,570 行)

`07_characters.py:4-13` 回答了"为什么人物必须是蒙皮网格":需求写死了"人物关节要做动画",而蒙皮在本项目里有个额外约束 —— **`InstancedMesh` 与 `BatchedMesh` 在 three r186 都不支持蒙皮**。所以每个人物是一个独立的 `SkinnedMesh`,一个 drawcall;"这一点直接决定了人数预算,也决定了这一块不能靠'多放几百个小人'来制造市井感 —— 那条路的成本是线性的。"

做法是**7 个姿态模板,而不是 7 个人**(`07_characters.py:15-20`):每个姿态一具身体,放进 `scene_characters.glb`;网页侧用 `SkeletonUtils.clone()` 取用,克隆时可改衣色、朝向、步速。于是"48 个人物"在网页里是 48 次 clone,而模型只有 7 具。

`07_characters.py:22-24` 记了一个具体坑:**克隆必须走 `SkeletonUtils.clone()`。直接 `Object3D.clone()` 会共享 `Skeleton`** —— "于是街上所有同姿态的人一起抽搐,而且看起来像'动画写错了',不像'克隆写错了'。"

**姿态即 rest pose**(`07_characters.py:26-33`):每个模板的 rest pose 就是它的姿态;行走的摆动由网页在这个 rest 之上叠加,所以 `walk` 模板的 rest 是"一动不动地站着",否则程序化的摆腿会叠在一个已经迈开的姿势上。rest pose 与网格**出自同一张关节角表**,见 `lib/rig_utils.py`。

### `08_assembly` —— 随身器物与 48 个实例(`blender/build/08_assembly.py`,1063 行)

"**这一层不建身体。**"(`08_assembly.py:4`)它做两件事(`08_assembly.py:7-9`):① 随身器物 —— 扁担(挑担)、撑篙(撑船),蒙皮到骨上;② 分布 —— 48 个人的姿态、位置、朝向、速度,写进 `src/data/actors.json`(`OUT_JSON` 定义在 `08_assembly.py:127`),外加一组仅供预览的标位柱。

文件头列了**三条必须写在最前面的判断**:

**一、随身器物的位置是「量」出来的,不是「定」出来的**(`08_assembly.py:15-26`)。扁担压在左肩上、穿左手的握点;撑篙挂在右手挂点骨的头的位置;独轮车的柄末端落在推车人两手之间。这三条约束的**目标值全在别处**(肩与手来自 `lib/rig_utils` 的骨骼表,车把来自 `06_props` 的几何),所以做法是:调 `RG.fk()` 算骨头 → 从骨头取点 → 连成轴线 → 建几何 → **回读复核**。注释里记了两次栽跟头:"34 个关节角符号整体反了,手臂长在肩后";"解推车姿态时把「相对父骨的角」当成了「世界角」,差 60mm"。"两次都是'我算过了',两次都不是证据。**回读才是证据。**"

**二、器物要跟着骨架的落地偏移走 —— 而这件事与直觉相反,已实测**(`08_assembly.py:28-46`)。`07` 建身体的顺序是"先蒙皮、后抬骨架",`08` 建器物的顺序必然是"先抬骨架、后蒙皮",两者**不等价**。实测(骨架下移 0.5m,观察一个 z=1.0 的点):先蒙皮后抬骨架 → 顶点落在 z = 0.5(跟着走了);先抬骨架后蒙皮 → 顶点落在 z = 1.0(没跟着走)。真实落差是 `punt` 姿态落地偏移 **−13.0mm**、`carry` **−5.9mm**(由 `RG.pose_landing` 实测,`08_assembly.py:43-44`)。所以 `_land_with_body()` 把器物显式对齐到骨架的世界矩阵,再**回读**。

**三**关于穿模检测(`08_assembly.py:60` 起)记了一次数值荒谬:"当场报出两个'深达 441.6mm'的穿模点,而那两个点的最近面在 420–630mm 之外 —— 躯干前后总厚才 0.264m,哪来的 441mm。"并指出马脚是那句"与身体最近 191.8mm":扁担压在肩上,怎么会离 191.8mm。

`08_assembly.py:181-192` 另有一条实现纪律:按**标签**找姿态模板,不按物体名找。

## 5. 尺度是怎么校验的

这是本文最该说清的一节。尺度校验**不是一件事,是三层**,职责不同,失败后果也不同。

### 5.1 第一层:`config._self_check()`,配置内部的不等式

导入 `config` 即执行(`config.py:1644` 定义,`config.py:1736` 无条件调用)。它检查各常数**互相之间**是否自洽,失败就 `raise AssertionError`(`config.py:1732-1733`)。逐条如下(每条都有具体理由,不是走过场):

| 检查 | 依据 | 行 |
|---|---|---|
| 实算通航净空 ≥ `CLEARANCE_MIN` | 用**实算值** `clearance_actual()` 而不是标称下限 —— "标称值只是给文档看的,几何才是真相" | `config.py:1647-1653` |
| 实算净空 > `Boat.AIR_MAX` | 否则"画中'船正穿桥'的情节不成立" | `config.py:1654-1658` |
| `DRAFT_MAX < River.DEPTH − 0.1` | 吃水过深船底触泥 | `config.py:1660-1664` |
| `River.WIDTH ≥ 2×BEAM + 2.0` | 河宽须容两船并行交会,与"漕运繁忙"的设定相容 | `config.py:1666-1668` |
| 拱轴半径与净跨自洽 | `r·sin(half_angle) == SPAN/2` | `config.py:1670-1673` |
| 两系统径向偏心 ≥ 半厚之和 | 否则两层拱骨会互相穿模 | `config.py:1674-1680` |
| 拱轴圆心高度与起拱点自洽 | | `config.py:1681-1682` |
| 屋面白名单真的禁掉了硬山 | | `config.py:1684-1686` |
| 桥轴与城门洞轴平面距离 > 15m | 否则"两层景深会叠在一起" | `config.py:1688-1694` |
| 金刚墙落在水面**之外** | 否则"拱脚泡在水里,会被淘空" | `config.py:1695-1700` |
| 岸上分区严格递增 | 否则街道会压在河道上 | `config.py:1701-1705` |
| 城墙内缘在街道带之外 | "城建在岸上,不能压到河" | `config.py:1706-1708` |
| `River.LENGTH ≥ 2×Site.FAR` | **补上来的**:漏了它真在场景里留过一个洞 | `config.py:1709-1718` |
| `Character.check_tables()` / `Assembly.check_tables()` | 按姿态名索引的表必须覆盖同一组姿态;"⚠️ 包在 try 里会失去意义 —— 这里就是要让它炸" | `config.py:1720-1724` |
| 推车握点 `PUSH_GRIP_Y > 0` | "写在注释里的数"与"几何真相"之间唯一的桥;错了推车人会扶在空气里,而预览图上只看着像"手离车把近了点" | `config.py:1726-1730` |

`River.LENGTH` 那一条值得记住形状:`config.py:1709-1713` 记着故障现象 —— 远景地裙在 `|x| < Site.ABUTMENT_FACE` 处给河留了通廊,若河道自身比 `FAR` 短,"通廊的尽头就是一块虚空 —— 俯视图上看得见,站在桥上顺河望下去也看得见"。**这一层完全不碰几何**,因此只能防"配置写错",防不了"builder 没照着配置建"——那是下面第二层的事。

### 5.2 第二层:`validate_scale.py`,几何即事实

`blender/tasks/validate_scale.py`(2631 行,126800 字节)是硬门禁。它的核心方法论是:**从场景里取物体,取真实的世界坐标顶点,量出跨度/矢高/净空/截面宽,再与 config 的声明比。**

这一点值得展开,因为它决定了这一层能抓到什么:

- 只对照 `config` 自查,抓不到"config 对、builder 建错";
- 量**真实几何**,才能抓到。所以注释里那句话是字面意思 —— **几何即事实**。

容差三档(`validate_scale.py:67-69`):

```
TOL_LEN = 0.008       # 精确几何量(截面、截面位置)—— 直弦离散化误差量级 ~1mm
TOL_PLAN = 0.02       # 平面位置(节点、轴心)
TOL_DECLARED = 0.05   # 与 config 声明的尺寸比 —— 声明值本身是推算值,不苛求
```

注意最后一档的取法:`TOL_DECLARED` 之所以最松,是因为**声明值本身是推算值**,不苛求 —— 这是把"尺子本身不准"算进容差里,不是放水。

`Check` 是 dataclass(`validate_scale.py:78` 起),`status` 取 `pass` / `fail` / `skip`,并有 `detail` / `expected` / `why` / `group` / `needs_stage` 字段。**`status == "skip"` 时必须写清为什么没量**(`validate_scale.py:84`)。

### 5.3 `skip ≠ pass`,与 strict 的用法

`skip` 与 `pass` 是两个状态,不是一回事。`run_all.py` 侧对应的是 `strict`:

```
strict = not missing          # run_all.py:195
```

即 **`strict` 只在"本次该跑的 builder 一个不缺"时才开**;开启后,本阶段**应验而未验**的条目判失败(`run_all.py:134-137`)。于是 `--stage 2` 那天,漏实现的形制断言会让构建失败,而 `--stage 1` 不会被阶段 2 才有的东西卡住。

`run_all.py:199-206` 专门为 `strict` 关闭时补了一行必打的警告,原因记在旁边:

> 少了 builder,strict 就是关的,报告里那句 `未执行 0` 于是**证明不了任何事** —— 它数的是"按 strict 口径该验而未验"的条目,而 07/08 没跑,人物那几条断言根本不进这个分母。我上一轮正是把这个 `0` 读成了"一条都没漏"。**数字本身没错,错的是我给它安的范围。**

当前读数(`blender/out/validate.json`):`stage 2`,`pass 59`,`fail 0`,`skip 0`,`overdue 0`;`checks 59`、`boundaries 24`。分组分布与逐条明细见 `docs/09-资产统计.md` 的形制门禁一节与 `docs/10-阶段验收记录.md`,本文不复制。

### 5.4 `BOUNDARIES`:这份校验**不**证明什么

`validate_scale.py:2441` 起是一个 24 条的 `BOUNDARIES` 元组。它是这个项目里最像"免责声明"、也最该保留的部分。它逐条写明这份校验的能力边界,例如:

- 它证明的是**几何与 config 一致**,**不是** config 与北宋现实一致;
- "无榫卯"这条只是**间接**支持(几何里查不到榫卯,不等于原构必定无榫卯);
- 屋面形制断言证明的只是**声明**里没有硬山;
- 手绘屋面的瓦垄间距量到的是**采样间距**;
- 7 座彩楼欢门只证明"本场景布置了 7 座";
- 贴图全是程序化生成的,不涉及任何实物扫描。

同一条边界在校验器里也重复了一次:`validate_scale.py:2480` 指出"城墙的收分 1.20m 与门道 5.6/19.3m 同为 Reliability B/C 的推算值"。

### 5.5 `tasks/` 下的其余脚本:先证明量具是好的

`blender/tasks/` 里除 `validate_scale.py` 与 `report_objects.py` 之外,还有一批脚本。它们有一个共同主题:**在信一个读数之前,先确认量具本身是好的。**

**反向测试 —— 让校验器先证明它会响。** 一个从不失败的校验器和没有校验器,在报告上长得一样:

- `negative_test.py`:往场景里注入 swap / pier / lash 三类已知错误,验证对应的形制断言**真的会失败**;
- `negative_attach.py`:验证 `_check_attached()` 抓得住"没装上的船件",模式为 `detach` / `detach_mooring`。

**探针 —— 分离"被测对象坏了"与"量具坏了"。**

- `probe_hull.py`:一个**被刻意保留**的探针,针对 `Object.bound_box` 的**局部坐标 vs 世界坐标**这个陷阱 —— 必须在取包围盒前调 `bpy.context.view_layer.update()`,否则拿到的是旧值。它用 `MOD.load_build("00_layout"/"01_bridge"/"02_river"/"03_boats").build()` 把前四个 builder 建起来,逐条船打印局部盒中心与世界盒中心,对照判据写在同一文件里。
- `preflight.py`:阶段 0 的能力探针,产物是 `blender/out/caps.json`(动态枚举那类陷阱就是在这里被撞出来的)。
- `probe_attributes.py` / `probe_attributes2.py`:两轮顶点属性导出探针,产物 `attr_probe.json` / `attr_probe2.json` —— §9 第 4 条那个结论就是这么来的(该目录下还留着 `_attrprobe2_A..D.glb` 等对照产物)。
- `probe_texture.py` / `probe_texture2.py`:贴图链探针,用 A/B/C/D 四种变体把"**我的 PNG 解码器错了**"与"**那些像素从来没被写进去**"分开 —— 这两种故障在图上长得一模一样。
- `probe_pixel.py`:问一张渲染图"这个像素上是什么"。
- `probe_shot.py`:同一件事的扫描线版本,另外记了**两个 Workbench 读数陷阱**(它是河道水色那次取样的工具)。
- `preview.py` / `preview_textures.py`:迭代预览。前者用 Workbench(`preview.py:205` 设 `BLENDER_WORKBENCH`),后者把每张贴图单独 dump 成 PNG,因为 **Workbench 不评估材质节点树**,在预览图里看不到程序化贴图。

这些脚本不是"工具洁癖"的产物。本项目反复出现同一个形状:症状出在读数上,病灶在量具上。它们的作用就是把这两件事分开。

### 5.6 第三层:导出侧的覆盖率与集合声明

`config.Export.CHUNKS`(`config.py:1586-1591`)声明了四个分块各自的集合归属,而分块与集合是两套命名。两处对不上,就会静默丢件。所以有两个方向相反的断言:

- `09_export.assert_full_coverage()`(`09_export.py:280`,在 `09_export.py:326` 被调用):查**结果** —— "每个网格物体都至少属于一个分块"。
- `report_objects.assert_declared_collections()`(`report_objects.py:513`):查"分块表里声明的集合**是不是真的建出来了**"。这是前者的**补集**,由 `run_all.py:261-262` 在阶段 ≥2 时调用,**放在导出之前** —— 查出来就不产出 GLB。

两个断言各自对应一个真实故障,而且**顺序上是一前一后**。

**第一个**(写在 `09_export.py:284-294`):`objects_in()` 按集合名**精确匹配**,而集合名是字符串 —— "只要 builder 那边写的名字与分块表差一个字,那一整块就静默不导出。实际发生过的正是这个:`04_buildings` 建的是 `buildings`,分块表里写的却是 `建筑群`,于是 `scene_props.glb` **从未被产出**,而构建依然报成功、验证 46 条全绿 —— 唯一的痕迹是日志里一行「[跳过] scene_props」,混在几百行导出日志里根本不会有人看见。" 修法不是去比对字符串,而是**检查结果**:有没有物体掉在分块表之外。掉一个就失败,并把它该往哪儿加一并报出来。

**第二个**(写在 `report_objects.py:517-527`):上一条补上之后,还剩一个查不出的情形 —— 声明的集合**根本不存在**,而它的内容被建进了**另一个**集合。`城墙城门楼` 当初就是:分块表里写着它,`04_buildings` 却把城墙与城门楼建进了 `建筑群`。于是"scene_core 里一座城墙也没有(首屏缺远景骨架),**而覆盖率断言一路绿灯** —— 因为城墙确实'在某个分块里',只是在**另一个**分块里"。

> 两个方向都查才闭环。放在**导出之前**跑:查出来就不产出 GLB,而不是先产出一批位置不对的文件再报错。

`report_objects.py:529-531` 另写了阶段规则:只对阶段 2 起生效 —— 阶段 1 只建虹桥,另外三块本来就还不存在,"那种缺失是**进程中的正常状态**,不是错误"。

预览件排除规则也是**两条同时满足**才生效(`config.py:1596-1608`):物体在 `PREVIEW_ONLY` 声明的集合里,**并且**带 `qm_preview` 标记。理由:

> 只按集合名排除的话,任何一次改名/手滑把真内容放进这个集合名,它就会**静默消失**在 GLB 之外,而 `assert_full_coverage` 也查不出来。两条一起要求之后,真内容缺标记 → 硬失败;预览件忘打标记 → 硬失败。剩下唯一能静默丢件的路径,是把真内容**同时**放进这个集合,并且亲手打上"这是预览件"的标记 —— 那已经不是手滑了。

对偶地,`09_export.assert_preview_marks()`(`09_export.py:232`)做的是反方向检查。

## 6. 导出、清单与 GLB 侧复核

### 6.1 分块:按"加载时机 + 更新频率",不是按类型

`config.py:1585` 一句话点明分块原则。四个块与各自的集合:

| 块 | 集合 | 理由(`09_export.py:8-11`) |
|---|---|---|
| `scene_core` | 河道 / 岸线 / 虹桥 / 城墙城门楼 | 首屏必须,先加载 |
| `scene_props` | 建筑群 / 彩楼欢门 / 柳树 / 道具 | 次屏 |
| `boats` | 全部船只 | 有独立动画 |
| `scene_characters` | 人物模板 | 有蒙皮 |

"这样加载进度条可以按块汇报,而不是'整体卡住'。"

注意这与"按资产类型切分"是两回事:建筑与船只都属于"场景静物",但船要动,所以单独成块。

各块的字节、面数、材质数,见 `public/models/manifest.json` 的 `files[]`(`manifest.json:7-61`)与 `docs/09-资产统计.md`;总量 `totalTris = 172032`、`totalBytes = 13347004`(`manifest.json:63-64`,约 12.73 MB)。

### 6.2 `manifest.json` 记什么

`public/models/manifest.json` 由 `09_export.py` 生成。它的字段设计有两点值得说:

**一、`exported` 与 `scene` 是两个不同的分母**(`manifest.json:65-91`)。`exported.objects = 232`、`exported.meshes = 225`,而 `scene.objects = 234`、`scene.meshes = 227`、`scene.armatures = 7`。差的那两个是仅供预览、按 §5.6 两条规则排除的物体。注释直接写在字段里(`manifest.json:68`):

> objects/meshes 为四块之和;materials 按块看 `files[].materials`,**不可求和**

不把 `materials` 求和,是因为同一个材质可以出现在多个分块里,加起来会得到一个没有意义的数。这类"两个数摆在一起会让人误读"的地方,manifest 选择把口径写进字段本身。

**二、每个分块都记了 `sha256`。** 但它在可复现性判据里的角色见 §6.5 —— **记录,不作为判据**。

`scene.counts.byKind`(`manifest.json:77-88`)给出按用途的物体计数(prop 56 / building 56 / boat 41 / tree 30 / celebration 21 / character 16 / gate 5 / terrain 5 / bridge 3 / water 1)。这套分类与 `qm_kind` 标签同源。

### 6.3 `tools/lib/glb.mjs` —— GLB 侧的独立量法

零依赖的 GLB 容器解析器。它提供 `parseGlb()`(`glb.mjs:54`)、`summarizeGlb()`(`:266`)、`summarizeGlbFile()`(`:431`)、`determinismKey()`(`:442`)、`imageHeader()`(`:201`),以及 `ND = 4`(`:41`,注释说明它与 `report_objects.py` 的 `ND` 一致)与 `round4()`(`:43`)。

它存在的理由是**独立性**:`report_objects` 量的是 Blender 场景,而这个模块量的是**导出的文件本身**。两份摆在一起比,才能说明"导出的内容就是这个数"(这正是 `run_all.py:250-252` 划下的边界)。

**为什么自己写、不用 `@gltf-transform/cli`**(`glb.mjs:4-16`),三条理由:

1. 那条 CLI 拖着 sharp 一类的原生二进制,**会把 `npm ci` 变脆** —— 而本项目对外的硬承诺之一是"全新 clone → `npm ci` → build 四步零手工干预","为一个只生成一张统计表的工具押上这条承诺,不值";
2. 它返回的是**它自己的字段名**,而报告里要写的判据是"对象数 + 每对象三角面 + 包围盒(1e-4)",这几个量的口径必须落在**这份文件**里,而不是落在别人的版本号里;
3. 要数的东西本来就不多 —— "JSON 块就是个规范化的结构体,拆它不需要一个库"。

**能力边界**(`glb.mjs:24-32`,逐条写在文件里):

- 只读,不改写、不校验规范合规性;
- 包围盒由 POSITION accessor 的 min/max 逐角点变换后取**轴对齐**包围盒 —— "物体被旋转时它比真实范围偏大(这是 AABB 的定义,不是算错),所以它适合判'位置与尺度是否漂移',不适合判'形状是否一致'";
- 图像尺寸读的是 PNG / WebP / JPEG 的**文件头**,三种以外的格式报 `null`,**不猜**;
- **不解析 accessor 的实际数据** —— 顶点数据的内容一律不管。

最后一条是这份工具最重要的边界:GLB 侧的复核**不检查顶点数据本身**。所以"某个 `flex` 属性有没有真的导出去"这类问题,不在它的射程内。

另有一处交叉说明写在 `glb.mjs:18-22`:项目里另有一个 `tools/check_texture_decode.mjs`,做的是**浏览器里的解码验证**(真实解码后的尺寸与色彩空间),与这里的"读文件头"不是同一件事,所以两份都留着。哪边是权威也写明了:**解码后的尺寸与色彩空间以那个脚本为准**,这里报的是**编码在文件里的**尺寸 ——"两者不一致本身就是个要查的信号"。

### 6.4 `tools/lib/qmids.mjs` —— 名字对照表

Blender 物体名 ↔ `qm_id` 的对照表:`GLB_FILES`(`qmids.mjs:29`)就是那四个分块,查询走 `qmIdOf(map, blenderName)`(`qmids.mjs:81`)。

这个模块的文件头(`qmids.mjs:1-23`)记了一条**接口级**的坑,值得原样转述:同一个物体在两套命名里各有一个名字,而且**两边都要用** —— Blender 侧叫 `虹桥_桥面`(中文,人在 Blender 里看的是这个),网页侧叫 `bridge_deck`(`qm_id`,浏览器里查的是这个)。`blender/out/stats.json` 只有**前者**,`qm_*` 标签只记了名字没记值。于是"任何拿 stats 的名字去和网页里的标识比的脚本都会**静默不匹配** —— 不报错,只是判据永远为假"。这不是设想:`tools/perf/verify_spots.mjs` 第一版就这么错了,把虹桥判成"射线从构件空当穿过",真实原因是拿 `虹桥` 去比 `bridge_deck`,前缀不匹配。

唯一同时含有这两个名字的地方,是导出 GLB 的**节点 extras**(节点名是 Blender 物体名,extras 里是 `qm_id`)。所以对照表从 GLB 建 —— `qmids.mjs:17-19` 说这是权威来源,因为"它就是浏览器实际拿到的那份数据"。并附一条禁令:`⚠️ 不要在别处再手写一份名称对照` —— 手写的那份会和导出的那份慢慢分家,"而分家后症状是'某个物体在网页上找不到',且找不到的原因看不出来"。这正是本项目反复出现的那个形状:**读数看着正常,病灶在仪器上。**

### 6.5 `tools/verify_reproducible.mjs` —— 可复现怎么验

`tools/verify_reproducible.mjs`(363 行)跑**两次完整构建**,然后比。判据有两层,都落在统计量上:

- **场景层**:`blender/out/stats.json`;
- **产物层**:解包 `public/models/*.glb`。

两层的比对内容相同:**物体数量 + 逐物体三角面数 + 世界轴对齐包围盒**,容差 `1e-4`。

几处刻意的设计:

- **比对前先 `delete stats.meta`**。`stats.json` 的 `meta` 段含 `builtAt` 与 Blender 版本,每次都不同,不参与确定性比对 —— 这条也写进了 `report_objects.py:504`。
- **不只读退出码,还扫日志尾部的 `✗` / `⚠ 以下`**。这是对 §2.3 那次"退出码撒谎"的直接回应:退出码与日志末尾**两个都要看**。
- **哈希被记录,但不作为判据**。脚本会算 `sha256` 并存进 `blender/out/hashes.json`(`verify_reproducible.mjs:116`、`:140`),也会打印每个块的"相同 / 不同"(`:304-307`)—— 但打印出来的**判据**是另一行:`判据 对象数 + 每对象三角面 + 包围盒(容差 1e-4)`(`verify_reproducible.mjs:257`、`:59`)。判定失败时 `firstByteDiff()`(`:225`)会打出偏移量、十六进制与 UTF-8 上下文 —— 那是给人查原因用的,不是判据。
- `BLENDER = process.env.QM_BLENDER || 'D:/blender/install/blender.exe'`。

结果写进 `blender/out/repro.json`。

### 6.6 一个必须说清的口径问题

`docs/10-阶段验收记录.md` 里记的 `boats.glb` 字节数与构建时间,来自**更早的一次构建**(831136 字节)。当前 `public/models/manifest.json:40` 记的是 `830436`,`builtAt` 为 `2026-09-18T06:12:51+00:00`( `manifest.json:5`)。

## 8. 导出链路里有没有降级/简化

直说结论:**没有运行时 LOD;但确实存在若干**在建模期完成的**简化与一个有损参数。**

### 8.1 没有的东西

**没有运行时 LOD 切换系统。** `qm_lod` 这个标签确实存在(近/中/远,`tag_utils.py:44`),也确实被写进物体(`tag_utils.py:272`),但它只在三处被消费:

- Blender 侧统计与预览:`04_buildings.py:1126`、`report_objects.py:265`、`preview.py:1321`;
- 报表:`tools/stats_report.mjs:286`;
- 性能工具:`tools/perf/once/emitters.mjs:43`、`tools/perf/once/inventory.mjs:32,78`。

**`src/` 里没有任何一处读 `qm_lod`。** 也就是说,它当前是一个**分类与统计用的标签**,不是驱动切换的开关。页面侧读的是别的标签:`qm_kind`、`qm_id`、`qm_anim`、`qm_pivot`、`qm_axis`、`qm_beached`、`qm_folded`、`qm_reflect`、`qm_actor`、`qm_pose`、`qm_robe`、`qm_flex`。

**没有几何压缩。** `config.Export.GLTF_KWARGS`(`config.py:1621-1635`)里没有任何压缩开关;全仓库检索 `draco` / `meshopt`,命中的只有 `blender/API_NOTES.md` 的实测记录、`blender/out/caps.json` 的能力清单、`blender/out/attr_probe.json` 的探针结果,以及 `blender/tasks/probe_attributes.py:170-172` 的探针本身。**生产链路里没有启用**,`public/` 下也没有 `draco/` 或 `meshopt/` 目录(当前只有 `fonts` / `models` / `original`)。API_NOTES 第 5 节记的是"这台机器上内建可用"(`API_NOTES.md:121-136`),可用 ≠ 已用。

### 8.2 真有的简化,逐条

下面这些是**导出链路**上的。形制与几何层面的简化另有一批,写在各自的 builder 里(虹桥的逐点穿插见 §3 `01_bridge`,河床见 `02_river`,船壳见 `03_boats`,屋面与城墙见 §7.3),不在这里重复。

1. **远景柳树的枝条数打折,发生在建模期。** `Tr.N_STRAND_FAR = 0.40`,`06_props.py:270` 在生成枝条时就乘上这个折扣;`06_props.py:944-946` 写明"这个折扣发生在建模里,不是在渲染里"。近景与远景的分野是 `near = sl["band"] == "near"`(`06_props.py:946`)。

2. **`flex` 顶点色属性只给近景。** 近景柳树带 `flex="flex"` 与 `anim="sway"`(`06_props.py:978`),另一处近景用 `anim="wind"`(`06_props.py:1059`);统计口径也分开记(`06_props.py:986`、`06_props.py:1100`)。所以"风动的柳条"只存在于近景,远景没有这个属性 —— 这不是渲染时的开关,是**导出时就少了一份顶点属性**。

3. **贴图接线表把材质复杂度压到 22 个材质、一张接线表。** `config.py:1460-1463`:"全场景 22 个材质、44 处 `MeshBuilder.build()` 调用点;把接线分散到那 44 处,就等于把'别忘了'摊到 44 个地方。"接线收进 `Texture.MATERIAL` 之后,接入 = 在这里加一行。

4. **有两张贴图被显式判定为不接。** `Texture.UNUSED`(`config.py:1549-1565`):`tile_flat`(板瓦是筒瓦屋面下的底瓦层,本模型的屋面只建了垄的起伏,没有分层做出底瓦几何,因此这张图没有可附着的面)与 `lattice`(它是镂空遮罩不是高度场;格子窗当前靠几何棂条表达,不用 alpha 贴图)。这里还有一处自我更正值得原样保留:`config.py:1554-1556` 写着这张图**并未被烤出** —— "烘焙是惰性的(只有材质去 `get_maps()` 要才会生成)……先前这里写的是'已按 KIT 烤出、成本已付',那是错的:成本不是已付,是**根本没发生**。"

5. **预览件不进 GLB。** 规则与双向断言见 §5.6;产物侧少了 2 个物体(`manifest.json:66-72`)。

6. **`export_apply: True`**(`config.py:1623`):导出前应用修改器。场景里唯一的修改器是蒙皮用的 Armature 修改器(`rig_utils.py:334`)。

7. **`export_animations: False`**(`config.py:1631`),注释给的理由是"人物行走完全由 JS 程序化驱动,不给任何 AnimationClip";`export_skins: True` 保留蒙皮。这不是简化几何,是**把动画从资产里移出去**,代价是网页侧必须自己驱动骨架。

8. **分块本身**也可以看作一种加载期的降级安排:首屏只加载 `scene_core`,而不是等四个块全到齐(§6.1)。

### 8.3 有损参数与未验证项

**WebP 有损编码,质量 85。** `config.py:1619` 的 `IMAGE_QUALITY = 85`。围绕它的注释(`config.py:1611-1618`)是本文必须原样转述的一段:

> 这是**一个有损参数,而它同时作用在 albedo、法线、粗糙度三种图上**:Blender 的导出器只给一个全局质量,分不开「albedo 有损、法线无损」。有损压缩法线会在斜面上留下块状痕迹,所以取 85 而不是 75(默认值)。这一条没有实测过"到底看不看得出来",**不许当成已验证**:要判断它,得在浏览器里对着斜屋面看 —— 阶段 4 的截图会做这件事。在那之前,`docs/05` 里不许出现「贴图无可见损失」这类话。

选 WebP 而不是 PNG,不是偏好问题,是被体积逼出来的。`09_export.py:26-30` 记着实测:阶段 2 第一次全量产出的四个 GLB 共 **37.84 MB**,其中 **27.7 MB 是 PNG 贴图**(逐块量过:scene_core 21.26 MB 里 18.83 MB 是 18 张 PNG,scene_props 12.82 MB 里 5.93 MB 是 27 张),"几何只占 9.8 MB。计划里的体积预算是 22 MB,超出的部分**全是贴图编码**,不是模型做多了"。

另外,`09_export.py:32-34` 记了选择器本身的一次教训:图像格式不是写死的,而是**先探测本机导出器认不认 WEBP**;"「去哪儿问」这一步我走错过一次"—— 同一个算子有两个 RNA。这个教训的完整版在 `API_NOTES.md`。

## 9. Blender API 经验(`blender/API_NOTES.md`)

`blender/API_NOTES.md`(181 行)是阶段 0 的产物:8 节实测笔记 + 一张"对计划的修正汇总"表。文件开头就写明它的性质(`API_NOTES.md:3-6`):"本文件记录的是**在本机实际跑出来的**结果,不是抄文档来的。每条都注明了验证脚本,可以重跑复核。"环境是 `Blender 5.2.2 LTS` / `Python 3.13.13` / `numpy 2.3.4`,一律以 `--background --factory-startup` 运行;验证脚本是 `blender/tasks/preflight.py` → `blender/out/caps.json`、`probe_attributes.py` / `probe_attributes2.py` → `attr_probe*.json`。

八节标题即其结论。几条影响最大的:

1. **动态枚举只能用一个非法值去问。**(`API_NOTES.md` 第 1 节)RNA 对 `scene.render.engine` 这类动态枚举**少报**,因为插件注册的引擎不是 RNA enum item。读当前值总是安全的;非赋值不可时,放进 `try/except TypeError`,异常会把所有合法值列出来。

2. **同一个属性,类 RNA 与实例 RNA 会给不同的答案。** 这条是从 API_NOTES 的探针手法长出来、又写进 `09_export.image_format()`(`09_export.py:124-164`)的。要问"本机导出器认不认 WEBP",必须读 `bpy.ops.export_scene.gltf.get_rna_type()`(实例 RNA);类 RNA `bpy.types.EXPORT_SCENE_OT_gltf.bl_rna` 读同一个属性,`enum_items` 实测返回**空列表** —— 而 config 里明明白白写着这台机器的枚举是 `AUTO / JPEG / WEBP / NONE`。"读空列表就会把「支持」判成「不支持」,于是次次退回 PNG。"实例 RNA 万一也空还有后手:往 `default` 上写一个非法值,让报错把合法值列出来。两条都问不出来才退回 AUTO,**且必须打出声**:"静默退回会让人以为体积已经压过了,而实际一个字节没省。"

3. **`--factory-startup` 仍会载入 Cube / Camera / Light。**(第 3 节)也就是说"出厂设置"不等于"空场景"—— 这是 `clear_scene()` 必须存在的现实背景之一。

4. **`export_colors` 已被移除,换成 `export_vertex_color`**,取值 `MATERIAL` / `ACTIVE` / `NAME` / `NONE`(第 4 节)。原计划是"靠 `export_attributes=True` 带出 `flex`",实测结论是:颜色属性确实可以,但**默认的 `MATERIAL` 模式会把同一个颜色属性重复导出两份**(COLOR_0 + COLOR_1),文件还更大(`API_NOTES.md:178`)。所以 `config.py:1627-1629` 选了 `NAME` + `flex`。同节还记了一条网页侧的连带发现:GLTFLoader 会**自动**把 `material.vertexColors` 置为 `true`,网页侧必须自己改回来(`API_NOTES.md:179`)。

5. **Draco / MeshOptimizer 内建可用**(第 5 节,`API_NOTES.md:121-136`):实测导出成功,Draco level 6 得 1180 字节并带 `KHR_draco_mesh_compression`,MeshOpt 得 2048 字节并带 `EXT_meshopt_compression`。第 181 行的修正汇总表里,这一条对应的是"不引入 `@gltf-transform` 这个依赖"。**注意:可用不等于已启用**,见 §8.1。

6. **WebP 原生可写**(第 6 节)。这是 §8.3 那 27.7 MB 问题的解法前提。

7. **命名漂移与废弃项**(第 7 节,`API_NOTES.md:153-164`):`Material.use_nodes` 与 `World.use_nodes` 均已标记废弃(预计 Blender 6.0 移除);新建材质的 `use_nodes` **默认为 true**,直接取 `BSDF_PRINCIPLED` 即可,**不要**再写 `mat.use_nodes = True`(会触发 `DeprecationWarning`);节点必须按 `type` 查而不能按名字查 —— 非英文界面下节点名是本地化的。还有一条顺带发现:WORKBENCH 预览的底色走 `shading.background_type="VIEWPORT"` + `background_color`,**与 world 无关**,所以那行可以直接删掉,不需要找替代写法。

8. **`pixels.foreach_set` 的性能与内存**(第 8 节,`API_NOTES.md:166-170`):256² RGBA 写入耗时 **0.0001s**,可以忽略;真正的约束是内存 —— `float32` 中间数组占 `W*H*4*4` 字节,4096² 单张即 **256MB**。所以定下"**默认用 1024²,上限 2048²**"—— 这正是 §4 `tex_utils` 那两条尺寸规则的来源。

另有一节与建模链路关系不大,但同样推翻了原计划里的假设(第 2 节,`API_NOTES.md:37-49`):原以为"后台模式 EEVEE 不保证拿到 GPU 上下文",实测**三种引擎在 `--background` 下都能出图**。64×64 首帧耗时:`BLENDER_EEVEE` **21.163s**(一次性上下文/着色器编译开销)、`BLENDER_WORKBENCH` **0.168s**、`CYCLES` **0.164s**。所以"结论不变但理由变了":迭代期仍首选 WORKBENCH(快两个数量级),文档用图用 CYCLES。这一条直接决定了 `blender/tasks/preview.py` 用 Workbench 做迭代预览。

这八节之外,文件末尾那张"对计划的修正汇总"表把"原计划 → 实测 → 处理"逐条列出,共四行(`API_NOTES.md:176-181`),其中三行已散见上文。它的价值不在结论,而在**每一条都有一次实测垫底**。

## 10. 程序化建模 vs 手工建模:在这个题材上的取舍

最后说这个题材本身。这里只陈述**代码与结构能支撑的**取舍,不评价好坏。

**为什么是程序化。** 这个场景的规模:`scene.objects = 234`、`exported.objects = 232`、总面数 `172032`(`manifest.json:64-72`)。其中大量构件是**同形的重复**:第一系统 30 根等长拱骨、第二系统 44 根拱骨(`01_bridge.py:14-15`)、按开间重复的格子门、沿 Y 排布的建筑与柳树。这类重复用手工建模的边际成本是线性的,用程序化则是参数改一个数。`MeshBuilder` 把"几百根梁"合成"一个物体、一个 drawcall"(`bl_utils.py:375` 起),这件事手工做等于逐个合并。

**代价是什么。** 程序化的代价是**几何写法受约束**:

- 结构表达要能被参数化。真实的"逐点上下穿插"被简化成同心的内外两层(`01_bridge.py:29-31`),因为逐点穿插难以在参数化折线拱里稳定生成。
- 材质要按名归并。同名不同色是硬错误(`MaterialLibrary`),这意味着一个 builder 不能临时造一个只属于自己一处的材质。
- 复杂度要能被预算。`InstancedMesh`/`BatchedMesh` 在 three r186 不支持蒙皮,这条技术事实直接决定了"48 个人物只能靠 7 具模板 clone"(`07_characters.py:9-19`)。
- 可复现性要求**禁用某些工具**。`00_layout.py:24-26` 为了不让 Blender 版本间的噪声实现漂移,放弃 `mathutils.noise`,改用固定相位的正弦叠加。这是"手工建模不会遇到、程序化必须处理"的一类约束。

**哪些东西看起来像缺陷,其实是设计或已声明的边界。** 头没有五官、欢门只有 1 座有据、远景柳树少 60% 枝条、贴图是有损的 —— 这四条都是写在代码里的决定或声明,不是遗漏。`docs/08-已知局限与未做还原.md` 里有同类清单。

**判断这些的尺子在哪。** 三处:`config.py` 的 `_self_check()`(配置自洽)、`blender/tasks/validate_scale.py` 的 59 条断言与 24 条 `BOUNDARIES`(几何自洽 + 明确说不证明什么)、`tools/verify_reproducible.mjs`(两次构建给出同一批数)。**这三处之外的说法,本文不采信。**
