> 这份文件是阶段 5 要求里「提供详细提示词」的落点。
> 它同时是这次**实际使用体验测试的观察记录** —— 一份提示词交给 AI 自主执行后,
> 哪些要求真的落了地,哪些落空了。

---

## 怎么读这份文件

- **第一部分**是原提示词**全文逐字照录**,没有删改、没有润色。
  你要复现这个项目,或者拿它去做别的题材,从这份全文出发。
- **第二部分**是实际执行记录:做了什么、迭代了几轮、修了多少东西。
- **第三部分**对照提示词逐条检查**哪些要求留下了可见的痕迹**。
  这里只记录「能达到 `file:line` 的证据」,不做因果推断 ——
  我不能证明某条要求"导致"了某个结果,只能说那里**有痕迹**。
- **第四部分**是**偏离与未满足项**。这是这份文件里最该看的部分。

## 一、原提示词全文

以下为逐字照录。

```text
你是一名全栈开发者、3D 艺术家和 technical artist。请使用ecc相关技能或者其他技能和mcp服务完成一个《清明上河图》三维交互网页项目，可以参考这篇文章：https://mp.weixin.qq.com/s/zcmrL69zO1XTQDKT7fGIbQ?scene=1&click_id=1373097907。

## 一、项目目标

制作一个可以用浏览器打开的《清明上河图》三维交互作品，交付完整代码、资产与文档。

核心目标：
- 可交互、可自由改变视角的三维网页。
- 三维建筑、人物、船只必须有真实的空间结构，不是贴图背景板。
- 参考北京故宫藏张择端本，聚焦汴河、编木虹桥与两岸市井。
- 原画未交代的背面、尺度可以合理推定，但必须明确写出边界，不要宣称“完美还原”或“考古级复原”。
- 画面方向：旧木、青灰屋瓦、土色街道、低饱和衣饰、自然光照，呈现繁忙生活。
- 近景需要木构、船板、屋瓦、窗棂、布幌、竹篮、陶器等可观察细节；远景也要有街巷层次。

## 二、环境与限制

本地设备：请先检测当前环境，并假设设备为【在此填写你的设备，例如 Apple M4 / 16GB 内存 / macOS】。

不调用外部图像/视频/音乐生成 API，不使用付费云渲染。
联网只用于核对资料和获取免费依赖、开放授权素材，记录来源与许可。

## 三、技术路线

自行选择适合的免费工具。推荐路线：
- 使用 Blender Python 程序化建模，导出 GLB。
- 使用 Three.js 在网页实时渲染。
- 使用 Node.js + Vite 或类似工具构建本地项目。
- 你可以使用 Playwright 或 Puppeteer 启动无头浏览器，截取画面并检查渲染结果，根据截图修正。
- 所有依赖必须免费、可本地运行。

## 四、自主工作流（必须遵守）

你必须自主分阶段执行，每一阶段完成后实际构建、打开浏览器检查、修正问题，再进入下一阶段。不要一次性堆完所有细节后才发现基础错误。

至少包含以下阶段，但你可以根据实际情况调整顺序和迭代次数：

### 阶段 1：最小可运行场景
- 生成一个最简单的 Three.js 页面，加载一个 GLB 模型（例如一个简单虹桥占位）。
- 确保可以在浏览器中打开，能看到三维物体，鼠标可环视、滚轮缩放。
- 使用无头浏览器截图，确认渲染成功。
- 修正任何报错、空白、黑屏问题。

### 阶段 2：场景构建与细化
- 核对原画中虹桥形制、河道和舟船与建筑的关系，再生成三维场景。
- 虹桥应是开放的木构拱桥，交叠木梁、桥板、栏杆分别成形，不在河中央添加桥墩，不把虹桥做成带廊屋的普通石桥。
- 按虹桥、船运、市井、建筑近景、城市全景分配细节预算。
- 近景补足梁柱、瓦垄、门扇、窗棂、招牌、棚布、器皿和货物。
- 建筑的背面也应合理，避免只对单个镜头有效。
- 人物有符合场景的衣帽、基本面部与自然比例，分别安排走路、挑担、撑篙、摆摊。
- 人物与地面、船、柜台之间的相对位置必须核对。
- 输出可重复运行的建模脚本与可编辑工程；固定随机种子，记录对象数量。
- 静态建筑和动态对象分别组织，动态对象保留导出标签，方便网页驱动。
- 先检查虹桥全景和市井近景，再扩展规模。发现人物穿桌、悬空或船体穿岸等问题时，修正模型或运动逻辑，重新导出后复查。

### 阶段 3：网页交互与界面
- 把场景做成有完整界面的中文网页。视觉风格与宋代长卷主题协调，层次清楚，控件不遮挡关键三维内容，同时兼顾电脑和手机布局。
- 需要实现：
  1. 左键环视、滚轮缩放、右键平移，键盘移动观察位置。
  2. 五个景点按钮（虹桥胜景、汴河漕运、沿岸市井、街巷营造、城阙远眺），镜头平滑切换到对应场景。
  3. 虹桥、漕船、茶肆的空间标签；点击打开简介，再点“走近看看”。
  4. 舆图定位、横向浏览原卷、复原依据说明。
  5. 清晨、暖日、暮色；画质选择；动画、标签和线框开关。
  6. 自动巡游、隐藏界面、全屏、原创配乐开关。
  7. 真实加载进度，资源失败和图形上下文中断时有明确提示。
- 请使用真实按钮与状态，不做无响应的装饰控件。手动操作应退出自动巡游。自由漫游和近距离观察时，控制相机运动的稳定性。
- 完成后实际点击每类按钮，检查标签与三维位置的对应、移动端溢出、切换后状态是否一致，并记录尚未解决的问题。

### 阶段 4：动画、特效与性能
- 加入实时水面反射、细波、船体轻摇、人物关节动作、风动布幌、柳枝、轻烟和飞鸟，保持自然、克制。特效不应掩盖模型细节。
- 在你所填写的设备上以完整场景实际运行评估性能，不用空场景帧率代表成品。
- 静态几何按区域和材质合批，重复网格尽量共享或实例化；适当压缩 GLB。
- 对模型、纹理、阴影、水面反射与后期分别评估开销，提供可切换画质。
- 人物和船只动画采用时间增量计算，切换标签或时辰时不能重置出明显跳变。
- 展示真实 FPS、三角形和绘制调用读数；报告设备、画质、窗口尺寸与采集方式。保留画面与性能之间的实际取舍，不虚构稳定 60 fps。

### 阶段 5：交付与文档
- 把项目整理为适合公开发布到 GitHub 的仓库。
- README 突出这是实际使用体验测试，配真实截图，列出可运行功能和客观不足。
- 提供详细提示词、部署、实现原理、模型与音乐重建、录制剪辑说明。
- 必须保证新目录 git clone 后可以 npm ci、构建、打开网页；模型、字体、贴图和解码器都包含在运行资产中。
- 排除软件安装包、依赖目录、缓存、私密配置和大体积视频；记录第三方素材与许可。
- 发布后检查仓库文件、工作流结果和线上加载，说明哪些成果留在本地以及如何重建。

## 五、质量要求与边界

- 所有代码必须可运行、可复现。
- 每一轮迭代前做好版本标记，保留旧文件，新的主入口和当前版本写清楚。
- 如果某个细节无法从原画确定，明确写出你的推定依据和边界，不要伪造考古准确性。
- 性能数据必须真实，展示实际读数。
- 不要声称“完美还原”“考古级复原”“稳定 60fps”等未经证实的结论。
- 最终交付必须包含：完整项目目录、README、运行说明、构建脚本、模型资产、截图、第三方素材许可说明。

## 六、开始执行

请现在开始自主执行。先检测环境，安装必要依赖，建立项目骨架，然后按照上述阶段推进。你可以自行决定每阶段的具体实现和迭代次数。每完成一个阶段，使用无头浏览器截图检查，修正问题后再进入下一阶段。最终完成后，向我报告项目路径、运行方式、已实现功能、性能读数和已知不足。

如果你在过程中遇到无法解决的阻塞（例如缺少 Blender、无法安装依赖、硬件不支持 WebGL），请明确报告阻塞点和你尝试过的解决方案。
```

## 四、偏离与未满足项

这一节的存在理由:提示词是这次测试的**变量**,交付物是**结果**。
不把差异写出来,这份记录就没有用。

### 1. 五景点按钮的名字改了

提示词写的是「虹桥胜景、汴河漕运、沿岸市井、街巷营造、城阙远眺」,
实现用的是「虹桥、漕船、茶肆、城门、街市」(见 `src/data/spots.json`)。
五个位置与对应的场景是一致的,变的是**措辞**。
以代码为准 —— 照提示词去找按钮会找不到。

### 2. 版本标记的粒度没有达到要求

提示词要求「**每一轮迭代前**做好版本标记,保留旧文件」。
实际是:**阶段 1–4 合并成了一个提交**(`e400e67`),
阶段内那 29 处修复的中间版本**没有逐轮留档**。
只有阶段 0 是独立提交的。这是一条明确的未达标项。

影响:阶段 1–4 的很多中间态现在无法复原,只能从 `docs/10` 的文字记录里
知道"当时是什么样、怎么改的"。

### 3. 两处与原画扫描件要求不符

- 切片高度是 **732** 而非要求的 900;
- **画卷方向与要求中所述相反** —— 本卷自右向左读。

两条都记录在 [`../public/original/CREDITS.md`](../public/original/CREDITS.md),
那里还写明了它的核实深度(许可引文来自搜索摘要,因本机网络对 Wikimedia
会重置连接,未能直接读取页面)。

### 4. "参考这篇文章"未能核对

提示词第 1 行给了一个微信公众号链接。该链接**未作为依据使用**,
仓库中也没有任何地方引用它的内容 —— 因为无法在无登录环境下稳定读取。
作品方向完全按提示词正文的六条核心目标确定。

### 5. 一项成因未定的缺陷,**没有**写成通过

`tests/effects.mjs` 的 B1 / E1 在早期 8 次运行里**失败 4 次**,
此后定向复现 12 + 40 轮、实跑 12 次**全部为 0**,但仍**不写成通过** ——
因为早期那 4 次失败**没有被解释**。见 `docs/10` 的「未定项」一节。

### 6. "发布后检查"曾经只写完了一半

提示词要求「发布后检查仓库文件、工作流结果和线上加载」。
写本文件时,这一条**只完成到一半**:仓库能构建能打开都验过了,
但**发布本身还没发生** —— 没有 remote、没有 `.github/workflows/`,自然也没有线上加载。

**后来补上了**,结果记在 [`04-离线部署说明.md`](04-离线部署说明.md) 第 5.3 节:
私有库先跑通 `verify`,转公开后 `verify` 与 `deploy` 双双 success,
线上地址实测能打开(无头 Chrome 三重校验通过)。

保留这条记录的原因是:这一条**当初就该被写成未完成**,而它在初稿里差点被
当成"已经做完" —— 因为"构建与校验全绿"看起来和"发布出去了"是同一件事。
它们不是。**构建全绿只说明产物是好的,不说明有人能访问到它。**
这与本文件第 5 条(B1/E1 成因未定故不写成通过)是同一种纪律:
**没做过的步骤不要写成做过了**,哪怕它看起来只差一步。

### 7. 三套依据等级口径并存,未统一

`src/data/basis.json`、`blender/config.py`、`docs/08` 各有一套 A/B/C 定义,
**互不相同**,目前并列存在。另外 `config.py` 里的 `Reliability` 枚举
**定义了但从未被引用**,39 处标注全是注释,无法被机器校验。
详见 `docs/01-复原依据与考据.md`。

## 五、如果要用这份提示词再做一次

基于这次的执行经验,几处**具体**的改法(不是泛泛而谈):

1. **把设备占位符填掉。** 原文那一行是空的(见第四部分开头)。
   另外「在你所填写的设备上评估性能」这一条因此失去了指代对象。
2. **把"每一轮迭代前做好版本标记"改成可检查的形式**,
   例如「每个阶段至少一个提交,阶段内修复也各自提交」。
   现在这条要求**没有留下任何可核对的产物**(见第四部分第 2 条)。
3. **给"找不到按钮就说明名字对不上"这类风险加一句**:
   如果界面文案可以自由改写,请在提示词里说明"以文档记录的最终命名为准",
   否则读者会按提示词里的名字去找。
