# 录制剪辑

> **一句话结论:本作品交付的是静态展示图,不是视频。**
> 仓库里既没有视频录制脚本,也没有任何视频文件(第 8 节有核查方法与命令)。
> 本篇的主体是**截图的两条流水线**,以及**怎么把你 clone 下来之后看不到的那 300MB 重建出来**。

本篇所有数字都是实测读数,不是标称值。采集环境与 `docs/05-性能测量报告.md` 相同:
无头 Chrome 153 / ANGLE(D3D11)/ NVIDIA RTX 3060 Laptop,服务为 `scripts/serve-dist.mjs`。

## 1. 两类截图,分工不同

这是本篇的核心区分。`tools/capture_showcase.mjs` 的文件头(`capture_showcase.mjs:5-9`)
把它写得很直白,这里照抄:

| | `tools/perf/shot.mjs` | `tools/capture_showcase.mjs` |
|---|---|---|
| 一次产出 | **一张** | **一组 17 张** |
| 用途 | 给**测量**用 | 给**展示**用 |
| 单张失败 | **即退出** | **不中断整组**,记进 manifest |
| 产出物 | 证据 | 发布物(README / docs 引用) |
| 压缩 | 不许有损 | 一律转 WebP |

### 1.1 `tools/perf/shot.mjs` —— 证据

文件头(`tools/perf/shot.mjs:2-9`)写的是它"不只是拍张图",而是同时做三件校验:

1. 渲染器必须是真 GPU(ANGLE/NVIDIA),退到 SwiftShader 就直接失败退出(`:157-165`);
2. 画面必须非空白 —— 用像素统计,不靠肉眼(`:166-171`);
3. 控制台不能有未捕获异常(`:240-242`)。

这三条不是形式主义。无头 Chrome 可能**静默**退到 SwiftShader 软件渲染,那种帧时毫无意义、
而画面看起来完全正常(理由记在 `docs/05-性能测量报告.md:17-19`;`shot.mjs:157-162` 就是这一条
在代码里的落点,失败信息还顺带指出该查 `--use-angle=d3d11`)。

用法(`:11-13`):

```bash
node tools/perf/shot.mjs --url http://127.0.0.1:4173/ --out screenshots/web/p0.png
node tools/perf/shot.mjs --url ... --out ... --w 390 --h 844 --mobile
```

参数表(`:19-49`,默认值取自 `:20-29`):

| 参数 | 默认 | 含义 |
|---|---|---|
| `--url` | `http://127.0.0.1:4173/` | 要拍的页面 |
| `--out` | `screenshots/web/shot.png` | 输出 PNG |
| `--w` / `--h` | 1600 / 900 | 视口 |
| `--dsf` | 1 | deviceScaleFactor |
| `--warmup` | 4000 | 热身毫秒(等 PMREM、阴影贴图、LOD 稳定,`:72-74`) |
| `--mobile` | 关 | 移动模拟(加 `--touch-events=enabled`,见 `cdp.mjs:42`) |
| `--allow-software` | 关 | 允许软件渲染(只在你明确知道自己在干什么时用) |
| `--no-blank-check` | 关 | 跳过空白检查 |

**它卡的不只是 GPU,还卡"URL 参数到底有没有落地"。** 这一段是踩出来的,
注释里记着坑(`:173-179`):

> `readUrlState()` 解析了 `q/tod/tags/hud/wire` 但没有任何地方消费,于是所有带
> `?q=high` 的截图都是 mid 档的,而快照里 `url` 字段写着 `q=high` —— **一个会撒谎的仪表**。

所以校验分两层,缺一不可:

- **store 层**:URL 里声明的期望值 vs 页面 `store.read()` 的真实状态(`:180-205`);
- **渲染侧层**(消费者那一侧):`?tod=` 要核**太阳高度** `sunY > 0`(`:193-198`);
  `?wire=` 要自己遍历场景数线框材质(`:206-215`),因为 `quality.report().wireframeMaterials`
  在内部分支为假时直接返回 0,**分不出"没生效"与"本来就关着"**(`:110-111`)。

`?tod=` 与 `?wire=` 这两个参数 2026-09-18 之前**从来没有生效过**(`:102-105`)。
只核 store 的话,每一张带 `?tod=` 的图都会判通过。

**⚠️ 失败时图已经写盘了。** 执行顺序是"取数(`:76-137`)→ 截图(`:139`)→ 写
`.state.json`(`:142-151`)→ 校验(`:153-242`)→ 报错退出(`:295-300`)。
也就是说,校验不过时 `--out` 指定的文件和同名 `.state.json` **都已经存在**。
判定看的是**退出码**,不是"文件在不在"。

另外两处值得记的细节:

- `.state.json` 与 PNG 同名同目录(把 `.png` 换成 `.state.json`,`:142`),内容含
  `url` / `viewport` / `sample` 三段;
- 关反射时**不打 RT 尺寸**(`:274-282`)。早先无条件打,于是 `?q=high&reflect=0`
  会印出"关 RT 512×256 每 1 帧" —— 尺寸是 mid 档留下的旧值、帧距是 high 档的,
  两个档位的读数拼在一行里。关掉时那张 RT 是**残留物,不是配置**。

### 1.2 `tools/capture_showcase.mjs` —— 展示图

它同样核对参数是否落地,理由写在 `:11-15`:

> 因为踩过。…… 图本身"看着挺好",没人会发现。**展示图比测量图更危险 ——
> 它会被放进 README,成为对外的说法。**

但它与 `shot.mjs` 的关键差别是**不中断**:

> 整组中断的话,后半段的图会缺,而缺图容易被当成"没拍"。(`:83-84`)

每张拍完就把"拍的时候**真实生效**的状态"记进 manifest(`:220-246`),
最后统一报问题(`:312-315`)。

## 2. 展示图流水线

代码在 `tools/capture_showcase.mjs`,输出目录写死为 `screenshots/showcase`(`:26`),
基准尺寸 1600×900(`:27-28`,移动端那张单独给 390×844)。

### 2.1 顺序

```
清空输出目录  →  逐张拍摄 + 核对参数  →  写 manifest  →  对比度关卡(量 PNG)
                                                       →  to_webp.py(验证后删源 PNG)
                       ↑                                              ↑
                  一张失败不中断                          对比度不过就**不**转
```

### 2.2 顺序为什么不能反

**第一步:先清空。**(`:115-120`)

```js
await rm(OUT_DIR, { recursive: true, force: true });
await mkdir(OUT_DIR, { recursive: true });
```

不清的话,改名/删掉一个镜头之后,旧文件会**留在目录里**并继续被 git 跟踪 ——
manifest 里没有它、README 也不引用它,但它就是在那儿,没人说得清是怎么来的(`:116-118`)。

**第二步:逐张拍摄,每张都核 URL 参数是否落到渲染侧。**(`:122-261`)

核对逻辑在 `auditState()`(`:90-108`),它只核 `q` 与 `tod` 两个参数,其中 `tod` 要**核两遍**:

```js
if (Math.abs(applied.tod - Number(expectTod)) > 0.02) {
  bad.push(`URL 要 tod=${expectTod},实际 store 里是 ${applied.tod}`);
} else if (rs && !(rs.sunY > 0)) {
  // store 对上了,但光照参数没落到光源上
  bad.push(`store 的 tod 是 ${applied.tod},但太阳高度读数为 ${rs.sunY} —— 没落到渲染侧`);
}
```

`:85-88` 记着这个函数的教训:

> 这个函数**第一版只对了 `store` 的读数**,于是 `?tod=0.2 / 0.78 / 0.95` 四张
> **全是白天**的图被判为"参数已落地"。store 有值不等于渲染动了 —— 这一条现在写进判据里:
> **凡是声称改了画面的参数,都要在"消费者那一侧"再核一次。**

拍摄内部顺序(`:132-150`):设视口 → `goto` → `waitForReady`(上限 120s)→
`sleep(4500)` 热身 →(需要开面板时才点)→ 取数 → 截图。
热身是必须的,不热身的话**第一帧的开销会污染记进 manifest 的帧时读数**(`:135-137`)。

面板用**属性选择器**点,不按文字点(`:30-36`、`:142-146`):

```js
const b = document.querySelector('[data-panel=' + JSON.stringify(shot.ui) + ']');
```

> 按文字点的话,哪天把「舆图」改成「地图」,脚本就静默地点不到东西,
> 拍出来的还是一张没有面板的"正常"图。(`:33-35`)

点不到就直接记一条 problem(`:147-149`),不静默。点完还要等 1400ms ——
面板有入场动画,动画没走完就截,拍到的是半透明的中间态(`:140-141`)。

**⚠️ 三角面/drawcall 取 `passStats` 的分解值,不取 `renderer.info.render`。**(`:156-159`)

后者是主 pass + 阴影 pass + 反射 pass 的**累加**;直接引它会把"主 pass 12 万面"
说成 40 万面,或者反过来让人以为主 pass 有 40 万。同一个坑见 `docs/05` 第 6 节。

**第三步:先写 manifest,再跑判定。**(`:266-308`)

这一段注释值得整段读(`:266-273`):

> ⚠️ 这一段必须写在**所有判定之前**。原来的顺序是「先跑对比度关卡、再写 manifest」,
> 而关卡判失败时直接 `process.exit(1)` —— 于是 manifest 根本没落盘。偏偏
> `check_contrast.py` 就是靠 manifest 里的 `textProbe` 才量得出对比度:
> **它要读的那个文件,被它自己引发的那次失败拦掉了。**
> 最后剩一堆没有任何记录的 PNG,谁也说不清是什么。
> **记录要先于判定落下来;判不判得过是之后的事。**

manifest 的结构(`:274-307`):`note` / `frameCaveat` / `countCaveat` / `units` /
`browser` / `base` / `generatedBy` / `shots`。每个 shot 有
`file` / `url` / `viewport` / `note` / `textProbe` / `applied`。

两个 caveat 是**故意**放在数据旁边的(`:282-283`):README 会引 manifest 里的面数/drawcall,
读者顺路就会看到 rAF 那三个数;不在这里说清它们是什么,它们就会被当成性能结论。
`applied.rAF` **不是作品的开销**,是无头 Chrome 的 rAF 节拍,空页面地板实测 6.10ms
(见 `docs/05` 第 3 节)。`applied.passes` 里的 `reflectionRenders` / `shadowRenders`
是**累计计数不是配置值**,随等待时长浮动,跨两次运行比它们没有意义(`:294-298`)。

**`file` 字段记的是 `.webp`,不是 `.png`**(`:221-222`)—— 那才是仓库里实际存在、
README 实际引用的文件。PNG 只是中间产物,转完就被删了。

**第四步:对比度关卡,而且必须量 PNG。**(`:317-343`)

`textProbe` 的坐标与颜色是**从 DOM 现读的**(`:181-205`),不在量具里写死:

> ⚠️ 从 DOM 读,不要在量具里写死坐标:哪天 CSS 挪了位置,写死的框会指着旁边
> 一块空背景继续量,而量出来的数照样"像那么回事"。(`:183-186`)

`display: none` 时 `rect` 全为 0,这里直接返回 `null`,由量具跳过(`:187-188`)。
实测:17 张里移动端那张(`17-yidong.webp`)的 `sub` 是 `null`,其余 16 张 title/sub 齐全。

关卡为什么排在这里、为什么不能放到转换之后(`:317-320`):

> **顺序不能反:对比度必须量 PNG。** WebP 是有损的,重编码会把字的边缘抹平,
> 量出来的是**编码器的误差**而不是 UI 的颜色。

工具是 `tools/check_contrast.py`。它自己的文件头(`check_contrast.py:4-13`)记着
为什么要做成一道**会判失败**的关卡:

> 顶栏是"文字压在**变化的**背景上"—— 背景是天空,而天空的颜色随时间、画质、机位全在变。
> 这种地方的对比度**没法靠看一眼判断**:同一行字在暮色图里清清楚楚,换到正午那张就糊了,
> 而人眼是先看见"能看清的那张"。实测过一次,结果很难看(2026-09-18):
>
> ```
> 标题   清明上河图        #e6dcc3  压在白天档的天上   3.70:1
> 副标题 三维长卷·汴河虹桥  #c9bda0                    1.96:1
> ```
>
> 正文的 AA 门槛是 4.5:1。两条都不够,副标题差了不止一倍。

量具本身也踩过坑(`check_contrast.py:15-21`):

> 第一版取"框内最暗像素当前景、最亮像素当背景"。…… 可这行字是**浅色**的,
> `#e6dcc3` 比底还亮,所以框内最暗的那个像素**根本不是字**,是遮罩与天的接缝。
> **判据方向反了,量具在夸自己。**

现在的口径(`:24-31`):前景 = `getComputedStyle().color` 的**声明值**(WCAG 通行口径);
底色 = 文字框内像素的**中位数**(字只占少数像素);另报"画出来最接近声明色的那个像素"
及其差值,差值大说明抗锯齿覆盖不足、**实际观感比声明值更低**,但这一项不参与判定。
门限用 WCAG 2.1:`AA_NORMAL = 4.5`、`AA_LARGE = 3.0`(`:69-71`),
大号字判定见 `threshold_for()`(`:99-108`)。

三条判据口径上的细节:

- 每张图各量一次,**取最差的那张**作为结论,不取平均 —— 白天档糊、暮色档清楚,
  平均下来会得到一个"还行"的假数(`:150-152`);
- 报**真正量过的那张 PNG 的名字**,不报 manifest 里的 `file` 字段(那个是 `.webp` 名),
  否则会印出 "03-chasi.webp 6.02:1",读的人去找 webp 核对,而 **webp 根本没参与测量**(`:176-179`);
- 缺 PNG 直接 `return 2`,并明说"对比度不能用有损的 webp 量"(`:185-189`)。

关卡失败时**不转 WebP**(`:345`),并提示"本组 PNG 已保留,方便直接开图看是哪一张最糊;
改的是 `src/styles/panels.css` 里 `.qm-topbar` 的遮罩,然后重跑"(`:338-343`)。

**第五步:`tools/to_webp.py`,转完**验证通过才**删源 PNG。**(`:355-365`)

为什么不给**全部**截图都转 WebP,`to_webp.py:9-18` 把这条分野写成了原则:

> · 展示图(`screenshots/showcase/`)给人看。有损压缩的代价没人看得出来,
>   而 17 张 PNG 有 19.3 MB,转完 1.6 MB。
> · 证据图(`screenshots/perf/`、`screenshots/web/` 里被探针引用的那些)是拿来做 A/B 的 ——
>   要比的差可能只有几个像素值,有损重编码会把那个差抹掉或者造出一个假的。
>   `tools/curate_screenshots.py` 因此**原样保留**被引用的 PNG。**同一个理由,两个方向。**
> 所以:**凡是要逐像素比对的,一律不转;凡是给人看的,一律转。**

先验证再删源(`to_webp.py:20-23`):

> ⚠️ 编码器写出一个 0 字节、或者一张纯黑/纯白的图,都不会报错;
> 若先删了 PNG,那张图就**永久没了**(仓库里只有这一份)。

`verify()`(`:45-66`)查三条:

| # | 判据 | 不过时的信息 |
|---|---|---|
| 1 | 产物存在且非 0 字节 | `没有生成文件` / `产物是 0 字节` |
| 2 | 尺寸一致 **且** 产物 `stddev` 最大值 ≥ 1.0 | `尺寸变了 WxH -> WxH` / `产物的像素几乎是纯色` |
| 3 | 至少压掉 **50%**(`MIN_SAVING = 0.5`,`:42`) | `只压掉 N%,低于 50% 的预期` |

第 2 条要转 RGB 再统计 —— webp 带 alpha 时 `ImageStat` 会按 RGBA 出四个数,
而我们只关心可见颜色有没有内容(`:57-59`)。任何一条不过:删掉半成品 webp、
**源 PNG 原样保留**并报错退出(`:94-99`,`:113-117`)。

默认质量 86(`:72`),可用 `--quality` 改,`--keep-png` 只转不删。

**最后:失败一律用 `process.exitCode`,不用 `process.exit(1)`。**(`:368-375`)

> Node 往**管道**里写 stdout 是异步的,`process.exit()` 不等它写完 —— 上面的报告会被直接截掉,
> 于是「工具失败了」和「工具什么都没说」看起来**一模一样**。这一条是踩出来的:
> 对比度关卡失败那次,连「共 17/17 张」那行都不见了,只剩 Python 的语法错,
> 害我先去查了几分钟的编码问题。

同一个位置上还有一条小的:`spawnSync` 不加 `shell: true`,那会触发 Node 的 DEP0190
(参数不转义直接拼命令)—— 这里不涉及用户输入,但一个要发布的仓库不该带着一条弃用警告跑(`:331-332`)。

### 4.2 实测:保留集是被"引用文本"推着长出来的

保留与否由**引用文本**决定,跟"它是不是重要"无关。这一点可以用三个时间点的
dry-run 读数直接看到 —— 仓库在这三个时刻之间只多了一些文档文字:

| 时刻 | 保留 | 将移动 | 这一次是什么进了保留集 |
|---|---|---|---|
| README 尚未落地,本篇也尚未写出 | 20 个 / 5.1 MB | 18 个 / 1.6 MB(全是 showcase) | — |
| 本篇写到磁盘之后 | **21 个 / 5.5 MB** | 17 个 / 1.6 MB | `showcase/manifest.json`(+1) |
| `README.md` 落地之后 | **37 个 / 7.0 MB** | **1 个 / 0.1 MB** | showcase 的 16 张 webp(+16) |

第二条的原因:本篇第 5.1 节按名字写了 `screenshots/showcase/manifest.json`,
而 `docs` 在 `SEARCH_DIRS` 里 —— 它**因此**进了保留集。
第三条的原因:`README.md` 在 `SEARCH_FILES` 里,而它按名字嵌了 showcase 的图
(`README.md:7`、`61-90` 等)。

**当前状态(实测):`screenshots/showcase/` 18 个文件里,17 个在保留集,只有 1 个不在 ——
`08-hun.webp`。**

原因是两边数目不一致:**拍摄脚本那一组是四个时辰**(`06-chen` / `07-wu` / `08-hun` / `09-mu`,
写成 `capture_showcase.mjs:54-59` 四条,其上方的分组注释写作"同一景点,四个时辰",`:45`),而
**README 那一节的标题是「三个时辰」**,只嵌了 `06` / `07` / `09` 三张(`README.md:72-75`,
表格下方还各配了一行说明:"清晨(太阳仰角 52°)" / "白昼(太阳最高)" / "暮色最深(太阳仰角 3°)")。
`08-hun` 因此没有任何文档按名字引用它。逐文件核对的结果:

```
KEEP  screenshots/showcase/01-hongqiao.webp
...
KEEP  screenshots/showcase/07-wu.webp
MOVE  screenshots/showcase/08-hun.webp     ← 唯一一个
KEEP  screenshots/showcase/09-mu.webp
...
KEEP  screenshots/showcase/manifest.json
```

⚠️ 所以**现在跑 `--apply`,被移走的是 `08-hun.webp`** —— 而它属于 README 正要展示的那一组。
这不是脚本的问题,是引用文本漏了一个。要留住它:在 README 或 docs 里按名字引用它,或者
接受它进 `_local/`。

三条口径上的注意:

1. **被移动的文件已经被 git 跟踪时,`--apply` 在 git 里表现为删除。**
   `git ls-files screenshots/ | wc -l` 实测为 38;
2. 正则要求**字面文件名**。写成 `screenshots/showcase/*.webp` 这种通配形式
   **匹配不上**(`*` 不在字符类 `[A-Za-z0-9_./\-]` 里),等于没引用 ——
   目录链接 `[screenshots/showcase/](screenshots/showcase/)` 同样不算;
3. **保留集还会随文档改动而变。** 上表三个读数就是同一台机器、同一份脚本、
   只改了几段 markdown 的结果。所以 `--apply` 之前**先跑一次 dry-run 看清单** ——
   这是脚本默认不 `--apply` 的原因。

## 8. 已知局限

1. **对比度关卡依赖前一步的 PNG。** 在已提交状态下单独跑 `check_contrast.py`
   会以退出码 2 报"缺 PNG"(实测)。要量就必须重跑整条采集。
2. **`check_contrast.py` 的"跳过"分支本次没有触发。** 它打印的提示是
   "N 张图没有 textProbe —— 多半是移动端把副标题 `display:none` 了"(`:213-214`),
   但本次 17 张**都**带 `textProbe`,所以 N = 0,那行不会打印。
   移动端那张的情况是 `sub: null`(DOM 侧 `rect` 为 0 时返回 `null`,`capture_showcase.mjs:187-188`),
   走的是内层 `continue`(`check_contrast.py:168-169`),**不计入 skipped**。
3. **`auditState` 只核 `q` 与 `tod` 两个参数**(`capture_showcase.mjs:90-108`)。
   `shot.mjs` 核得更多(`tags` / `hud` / `wire` / `reflect`)。展示图这一侧
   **没有**对 `ui`、`mobile`、`spot` 做参数落地判定 —— `spot` 是否生效只能事后
   从 manifest 的 `applied.camera` 反查(第 3 节就是这么做的)。
4. **`screenshots/_local/` 没有逐文件清单,也没有版本控制。** 它是过程记录,
   重跑同名探针会覆盖同名文件。第 6.2 节给的是"哪个目录由哪个脚本产出",
   不是"这 376 个文件各自怎么来"。
5. **重建不是逐字节复现。** 同一次采集重跑,`01-hongqiao` 的主 pass drawcall
   从 159 变成 158(第 6.3 节)。展示图的用途是"给人看",不是"当基准"。
6. **本文件写的对比度读数(6.02:1 / 8.22:1)来自本机 2026-09-18 那一次实跑。**
   它们是**那一次**的读数;换机器、换分辨率、改 `.qm-topbar` 的遮罩都会变。
7. **没有视频。** 第 7 节是核查结论,不是待办 —— 仓库里没有任何录制能力,
   `.gitignore` 里的 `recordings/` 只是一条"别提交大文件"的预留规则。
