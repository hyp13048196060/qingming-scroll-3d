# 离线部署说明

**一句话结论:全新 clone → `npm ci` → `npm run build` → 起一个静态服务,就能看到完整作品,
过程中不需要联网取任何运行资产、不依赖任何外部 CDN。**

本文是**操作性文档**,写给"拿到这个仓库、想把它跑起来"的人。因此下面每一条命令都在本机
实际跑过,数字直接抄自命令输出,不是照着配置文件推的。凡是**没跑过**的,文中会明确写
"未验证",不会写成"应该可以"。

> ⚠️ **本文的一条写作纪律**:配置文件的注释描述的是**意图**,代码才是事实。
> 第 2.4 节记录了一处两者对不上的地方 —— 配置注释说解码器"必须随构建产物落盘",
> 实测却发现当前代码根本没有加载任何解码器。以代码为准,如实写出。

## 1. 环境要求

### 1.1 Node 必须是 24.x —— 不满足会直接装不上

三处配置互相咬合,只有一处写了具体版本:

| 文件 | 内容 | 行 |
|---|---|---|
| `package.json` | `"engines": { "node": ">=24.0.0 <25" }` | `package.json:8-10` |
| `.npmrc` | `engine-strict=true` | `.npmrc:2` |
| `.nvmrc` | `24.18.0` | `.nvmrc:1` |

`engines` 给出的是**区间**(`>=24.0.0 <25`),`.nvmrc` 给的是**本机实际用的那个点版本**
(24.18.0)。`.npmrc` 里的 `engine-strict=true` 让 npm 把 `engines` 当成硬性条件而不是提示 ——
Node 不在 24.x 时 `npm ci` 会**拒绝安装**。

**实测**:`node -v` → `v24.18.0`,`npm -v` → `11.16.0`。

> ⚠️ **未验证**:我没有把 Node 换成 22.x 或 25.x 去实测那条拒绝安装的行为。
> `engine-strict` 的语义来自 npm 的配置约定,不是我在本机量到的。
> 如果你想确认,`nvm use 22 && npm ci` 一次就知道。

用 `nvm` 的话:

```bash
nvm use          # 读 .nvmrc,切到 24.18.0
```

### 1.2 为什么是 `npm ci` 而不是 `npm install`

**先回答"有没有 lockfile"**:有。

```
$ git ls-files --error-unmatch package-lock.json
package-lock.json
$ git status --porcelain package-lock.json
(空 —— 未修改)
$ node -e "const l=require('./package-lock.json');console.log(l.lockfileVersion, Object.keys(l.packages).length)"
3 87
```

即:`package-lock.json`(48,458 B,`lockfileVersion 3`,87 个包条目)**存在且已入库、当前无改动**。

选 `ci` 的理由:

- `npm ci` **只认 lockfile**,装出来的依赖树是锁定的那一棵;`npm install` 会按
  `package.json` 的 semver 范围重新求解,必要时还会**改写 lockfile**。
  对"同一份源码在两台机器上装出两个版本"这件事,`ci` 是能给出保证的那一个。
- `npm ci` 会先清空 `node_modules` 再装,不会留下上一次安装的残留。
- 本仓库的依赖全部是**精确版本**(`three: "0.186.0"`,没有 `^`/`~`),配合 lockfile
  与 `engine-strict`,整条链是可复现的。

**实测**(不破坏 `node_modules` 的干跑):

```
$ npm ci --dry-run
up to date in 5s
EXIT=0
```

> ⚠️ **未验证**:我没有真的执行一次完整的 `npm ci`(它会删掉 `node_modules` 重装,
> 在本机属于会打断其它并行工作的操作)。上面是 `--dry-run` 的结果,它证明了
> **lockfile 与 `package.json` 一致、无缺失依赖**,但不等于我从零装过一遍。

安装:

```bash
npm ci
```

### 2.2 `base: './'` —— 为什么是相对路径

```ts
// vite.config.ts:17-18
// 相对路径,使 dist/ 可以直接被静态服务器托管在任意子路径下
base: './',
```

Vite 默认 `base: '/'`,产物里所有引用都会写成 `/assets/xxx.js` —— 根绝对路径。
部署到 GitHub Pages 时站点在 `https://<user>.github.io/<repo>/`,根绝对路径会**全部 404**。

写成 `'./'` 之后,产物里是相对引用。**实测 `dist/index.html`**:

```html
<script type="module" crossorigin src="./assets/index-pULkds0y.js"></script>
<link rel="modulepreload" crossorigin href="./assets/three-BZfwVKBA.js">
<link rel="stylesheet" crossorigin href="./assets/index-zFExGo3o.css">
```

全是 `./` 开头。这条相对路径同时被两处依赖:

- `src/styles/fonts.css:20,28` 里 `@font-face` 的 `url("../assets/fonts/*.woff2")` ——
  注释(`fonts.css:12-13`)写明 CSS 里**不能**写根绝对路径,要交给 Vite 按 `base` 重写。
- `src/core/assets.ts:67-71` 的 `assetUrl()` 用 `new URL(rel, document.baseURI)` 解析模型地址,
  同样不依赖构建期注入的 base。

**实测(不是推断)**:我把 `dist/` 挂到一个子目录下、用一个只认目录结构的静态服务托管,
在真实 Chrome 里从子路径打开,结果见第 5.2 节 —— 页面正常起起来了。

### 2.3 解码器复制:`vite-plugin-static-copy` 把什么放到了哪里

```ts
// vite.config.ts:36-52
targets: [
  { src: 'node_modules/three/examples/jsm/libs/draco/*.{js,wasm}',   dest: 'draco',   rename: { stripBase: true } },
  { src: 'node_modules/three/examples/jsm/libs/basis/*.{js,wasm}',   dest: 'basis',   rename: { stripBase: true } },
  { src: 'node_modules/three/examples/jsm/libs/meshopt_decoder.module.js', dest: 'meshopt', rename: { stripBase: true } },
],
```

实测落到 `dist/` 的位置与体积:

| 目标目录 | 文件 | 字节 |
|---|---|---|
| `dist/draco/` | `draco_decoder.js` | 719,410 |
| | `draco_decoder.wasm` | 285,747 |
| | `draco_wasm_wrapper.js` | 58,763 |
| `dist/basis/` | `basis_transcoder.js` | 57,529 |
| | `basis_transcoder.wasm` | 527,333 |
| `dist/meshopt/` | `meshopt_decoder.module.js` | 29,256 |

合计 **1,678,038 B ≈ 1.60 MB**,6 个文件 —— 与构建日志的 `Copied 6 items.` 对得上。

#### `rename: { stripBase: true }` 不是可选项

`vite.config.ts:22-35` 用了一段很长的注释解释这件事,这里转述要点并给出实测依据:

`vite-plugin-static-copy` 4.x **一律保留匹配文件相对 root 的整条目录**
(4.x 已移除 v2 的 `structured: false`)。少了 `stripBase`,解码器会落到

```
dist/draco/node_modules/three/examples/jsm/libs/draco/draco_decoder.js
```

而 `DRACOLoader` 是去 `./draco/` 取的 —— 路径对不上。加了 `stripBase: true` 之后,
插件用 `../../..` 把中间目录抵消掉,`path.join` 归一化后正好落回 `dest` 根。
**上表的实测路径证实了这一点**(`dist/draco/draco_decoder.js`,没有中间目录)。

### 2.4 ⚠️ 一处配置注释与代码对不上的地方:解码器当前**没有被用上**

上面那三个目录确实被复制了,这一点没问题。但写本文时做了一项检查,结果与
`vite.config.ts:5-14` 那段注释描述的**场景不符**,如实记在这里。

那段注释说的是:"`DRACOLoader` / `KTX2Loader` 默认会去 CDN 取解码器 wasm,
所以要复制到本地、运行时按相对路径加载。"

**实测一:源码里没有任何一处引用这些解码器。**

```
$ grep -rn "DRACOLoader\|KTX2Loader\|MeshoptDecoder\|setDecoderPath\|setTranscoderPath" src/
(无匹配)
```

`src/core/assets.ts:22,136` 只 `import { GLTFLoader }`,没有挂任何解码器插件。

**实测二:四个 GLB 也确实不需要解码器。**

```
$ node -e "…读 GLB 的 JSON 块…"
scene_core         extensionsRequired: ["EXT_texture_webp"] | images: 24
scene_props        extensionsRequired: ["EXT_texture_webp"] | images: 24
boats              extensionsRequired: ["EXT_texture_webp"] | images: 12
scene_characters   extensionsRequired: ["EXT_texture_webp"] | images: 3
```

四块模型**只要求 `EXT_texture_webp`** —— Draco / Basis(KTX2)/ Meshopt 一个都没用到。
`EXT_texture_webp` 由浏览器自身的 `createImageBitmap` 解,不走 three 的那些解码器。

**实测三:页面运行时一次都没去取解码器。**

在真实 Chrome 里加载构建产物,记录全部网络请求:

```
总请求数: 11
   assets/index-pULkds0y.js    138 KB
   assets/three-BZfwVKBA.js    796 KB
   assets/index-zFExGo3o.css    15 KB
   models/manifest.json          2 KB
   assets/lxgw-wenkai-regular-CG7_ODO4.woff2    344 KB
   assets/lxgw-wenkai-medium-2urt-iL0.woff2     343 KB
```

**结论**:`dist/draco/`、`dist/basis/`、`dist/meshopt/` 这 1.60 MB 是**随包发出但当前不被加载**的。
它不影响首次加载体积(不请求就不下载),可以理解为给后续换压缩格式留的余量。
本文不把它写成"离线运行所必需"——实测它现在不是。

> 这与本项目记录在案的一类错误同形:**注释描述的是意图,代码没有实现它。**
> 只不过这一次的后果是"多复制了 1.6 MB 没人用的文件",而不是画面出错。
> 要不要保留,取决于后续是否会启用 Draco/KTX2 压缩,本文不替这个决定下结论。

### 2.6 构建产物的可复现性(有限观察)

我在同一天跑了 2 次 `npm run build`。其中 `three-BZfwVKBA.js`(815,267 B)与
`pluck-processor-ByzsmUqz.js`(16,020 B)在两次之间**内容哈希完全相同**(文件名里的

## 3. 本地预览

### 3.1 `dist/` 不能直接双击打开 —— 必须起 HTTP 服务

`dist/index.html` 引用的是 `<script type="module">`(ES module)。在 `file://` 协议下,
模块加载会被 CORS 挡掉,页面**不会报出显眼错误,只是白屏**。

**实测 A/B**(同一个真实 Chrome,同一份 `dist/`,只换协议):

| 加载方式 | `window.__QM_READY__` | 页面正文 |
|---|---|---|
| `file:///…/dist/index.html` | **`false`**(等待 25s 超时) | 空 |
| `http://127.0.0.1:4199/` | **`true`** | 完整界面(虹桥 / 漕船 / 茶肆 / 城门 / 街市 / 舆图 / 原卷 / 依据 / 设置 …) |

`__QM_READY__` 是页面自身在装配完成后置位的标志(见 `tools/perf/lib/cdp.mjs:180-195`)。
`file://` 那一行它始终是 `false`,连 `window.__QM__` 都没有 —— 脚本压根没执行。

### 3.2 仓库自带的静态服务器

**真实路径:`scripts/serve-dist.mjs`**(零依赖,只用 `node:http`)。

用法(抄自文件头 `scripts/serve-dist.mjs:9-12`):

```bash
node scripts/serve-dist.mjs --dir dist --port 4173
node scripts/serve-dist.mjs --dir dist --port 4173 --no-content-length
```

`package.json:14` 把它包成了:

```bash
npm run preview     # = node scripts/serve-dist.mjs --dir dist --port 4173
```

**为什么不用 `vite preview`**(`scripts/serve-dist.mjs:5-7` 写明):本作品要验证
"没有 `Content-Length` 时加载进度是否仍然准确",而 `vite preview` 关不掉那个响应头。
所以自己写了一个,并提供了 `--no-content-length` 开关去模拟分块传输。

**实测**:终端输出 `静态服务已启动: http://127.0.0.1:4199/  (根目录 D:\…\dist)`。
逐条探测:

| 路径 | 状态 | 字节 | Content-Type |
|---|---|---|---|
| `/` | 200 | 931 | `text/html; charset=utf-8` |
| `/models/manifest.json` | 200 | 2,120 | `application/json; charset=utf-8` |
| `/models/scene_core.glb` | 200 | 4,354,976 | `model/gltf-binary` |
| `/draco/draco_decoder.wasm` | 200 | 285,747 | `application/wasm` |
| `/basis/basis_transcoder.wasm` | 200 | 527,333 | `application/wasm` |
| `/meshopt/meshopt_decoder.module.js` | 200 | 29,256 | `text/javascript; charset=utf-8` |
| `/assets/pluck-processor-ByzsmUqz.js` | 200 | 16,020 | `text/javascript; charset=utf-8` |
| `/original/section1.jpg` | 200 | 749,537 | `image/jpeg` |

> ⚠️ **本机 4173 端口当时已被占用**(`EADDRINUSE`),所以上面用 `--port 4199` 实测。
> 这是本机环境状态,不是脚本问题。你那边若 4173 空着,`npm run preview` 直接用即可。

`--no-content-length` 模式实测生效:响应头变成 `Transfer-Encoding: chunked`,**没有**
`Content-Length`(`scripts/serve-dist.mjs:101-115`)。

### 3.3 两个必须知道的行为

**一、这个服务器有 SPA 回退,不存在的路径也返回 200。**

`scripts/serve-dist.mjs:83-91` 在文件找不到时回退到 `index.html`。实测:

```
$ curl -s -o /dev/null -w "%{http_code} %{size_download}\n" http://127.0.0.1:4199/nonexistent-xyz
200 931
```

**资源路径写错时你看到的是"200 + 931 字节的 HTML",不是 404。** 页面里表现为解析失败
或白屏。这不是假设 —— 上面网络记录里那条 `favicon.ico  1 KB` 就是活例子:
`index.html` 并未引用 favicon,`public/` 下也没有 `favicon.ico`(已确认不存在),
浏览器照例去要,服务器回了一份 931 字节的 `index.html`,`Content-Type: text/html`。

排查资源问题时**要看 Content-Type,不能只看状态码**。

**二、响应头带 COOP/COEP。**

`scripts/serve-dist.mjs:95-99` 发了:

```
Cache-Control: no-store
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: credentialless
```

注释(第 96 行)说明这是为将来接 `SharedArrayBuffer` 预留的。**当前构建不依赖这两个头**:
上面的网络记录里 11 个请求全部成功,没有跨源隔离的依赖。所以换成 GitHub Pages
(不会发这两个头)不影响运行。

## 5. 部署到 GitHub Pages

### 5.1 为什么子路径能跑

`base: './'` 让所有引用变成相对路径(见 2.2)。GitHub Pages 的项目站点
`https://<user>.github.io/<repo>/` 是一个**子路径** —— 只要 `dist/` 的内容原样放到该子路径根下,
相对引用就会正确解析。反过来,若 `base` 是默认的 `'/'`,所有 `/assets/...` 都会 404。

### 5.4 手动部署(不依赖 CI)

不需要改任何配置:

```bash
npm ci
npm run build
# 然后把 dist/ 里的全部内容上传到目标子路径的根目录
```

任何能托管静态文件的地方都行(`gh-pages` 分支、对象存储、内网 nginx)。
**实测边界**:第 5.2 节验证的是"子路径 + 普通静态文件服务",没有验证过具体某家的托管平台
(缓存策略、MIME 配置、重写规则各家不同)。
